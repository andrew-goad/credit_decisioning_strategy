Great. Since it ran cleanly, the review pass should focus on one question:

Does the synthetic portfolio behave the way the BRD says it should behave?

The easiest way to do that is to review outputs in layers, from broadest to most detailed.

Review order

1. Start with population integrity

Run the record count and basic completeness checks first.

Look for:

  • application count equals your parameter
  • no unexpected nulls in core fields:
    • product_type
    • score_band
    • credit_score
    • annual_income
    • requested_amount
    • base_apr_for_payment_calc
    • monthly_payment_proxy
    • payment_to_income_ratio
    • estimated_pd
    • estimated_lgd
    • expected_loss_amount

Use something like:

SELECT COUNT(*) AS row_count
FROM credit_decisioning_sim.synthetic_applications;

SELECT
    SUM(CASE WHEN product_type IS NULL THEN 1 ELSE 0 END) AS null_product_type,
    SUM(CASE WHEN score_band IS NULL THEN 1 ELSE 0 END) AS null_score_band,
    SUM(CASE WHEN credit_score IS NULL THEN 1 ELSE 0 END) AS null_credit_score,
    SUM(CASE WHEN annual_income IS NULL THEN 1 ELSE 0 END) AS null_income,
    SUM(CASE WHEN requested_amount IS NULL THEN 1 ELSE 0 END) AS null_requested_amount,
    SUM(CASE WHEN base_apr_for_payment_calc IS NULL THEN 1 ELSE 0 END) AS null_apr,
    SUM(CASE WHEN monthly_payment_proxy IS NULL THEN 1 ELSE 0 END) AS null_payment,
    SUM(CASE WHEN payment_to_income_ratio IS NULL THEN 1 ELSE 0 END) AS null_pti,
    SUM(CASE WHEN estimated_pd IS NULL THEN 1 ELSE 0 END) AS null_pd,
    SUM(CASE WHEN expected_loss_amount IS NULL THEN 1 ELSE 0 END) AS null_expected_loss
FROM credit_decisioning_sim.synthetic_applications;

What you want:

  • row count exactly right
  • null counts all zero, except loan_term_months may be null for revolving if you kept it that way

2. Check the portfolio mix

This tells you whether the engine is honoring the parameter block.

Look for:

  • product mix close to targets
  • score-band mix close to targets

The built-in QA queries already do this. Compare the actual percentages to your configured weights.

What you want:

  • close, but not necessarily exact to the sixth decimal because of finite row count
  • with 50,000 rows, it should be very close

Healthy result example:

  • Mortgage around 30%
  • Revolving around 25%
  • Auto around 20%
  • Personal around 15%
  • HELOC around 10%

And score bands roughly aligned to your parameter block.

If something is materially off, that points to assignment logic, not realism logic.

3. Validate directional realism by score band

This is the most important review step.

You want to confirm that the portfolio behaves directionally like real credit populations.

Use the built-in score-band summary. Focus on these patterns:

Credit score

Should rise cleanly from deep subprime to super-prime.

Income

Should generally rise as score improves, but not perfectly. You do not want a mechanical staircase with no overlap.

DTI

Should generally worsen as score worsens.

Utilization

Should generally worsen as score worsens.

Delinquency

Should rise materially as score worsens.

Major derog / bankruptcy

Should be rare in stronger bands and much more common in weaker bands.

PTI

May worsen somewhat in weaker bands, but this may be less clean than DTI because PTI is structure-driven.

PD

Should increase clearly and materially as score weakens.

What you want:

  • clear directional progression
  • but not perfect monotonic “robotic” behavior at the row level

Red flags:

  • prime and subprime averages look too similar
  • utilization or delinquency is flat across bands
  • income increases too perfectly with no overlap
  • PTI is bizarrely better in risky segments with no structural reason

4. Check product realism

Now move from score logic to product logic.

Use the product affordability / loss review query.

For each product, review:

  • average requested amount
  • average APR
  • average monthly payment
  • average PTI
  • average PD
  • average LGD
  • average expected loss
  • total expected loss

What you should expect conceptually:

Mortgage

  • highest requested amounts
  • relatively low APR
  • large monthly payments, but not necessarily the worst PTI
  • lower LGD than unsecured products
  • meaningful expected loss because exposure is large

Revolving

  • smaller requested amount / line proxy
  • very high APR
  • minimum payment proxy keeps payment lower than installment would
  • PD may be relatively elevated because utilization matters
  • highest LGD or near highest

Auto

  • moderate amount
  • moderate APR
  • term structure should reduce burden
  • PTI should often be manageable relative to personal loans

Personal loan

  • smaller balances than mortgage/HELOC
  • higher APR
  • shorter terms
  • can generate more affordability pressure than balance alone suggests

HELOC

  • larger balances
  • lower payment burden because of interest-only proxy
  • PTI can look better than raw exposure suggests
  • lower LGD than unsecured products

Red flags:

  • mortgage average amount too low
  • revolving average APR too low
  • personal loans having easier PTI than auto on average without explanation
  • HELOC looking indistinguishable from mortgage or revolving

5. Review the PTI thesis directly

Because your BRD centers the architecture on structure → payment → PTI → PD, this needs its own check.

Run a few summaries by PTI bucket:

SELECT
    CASE
        WHEN payment_to_income_ratio < 0.05 THEN '<5%'
        WHEN payment_to_income_ratio < 0.10 THEN '5%-9%'
        WHEN payment_to_income_ratio < 0.15 THEN '10%-14%'
        WHEN payment_to_income_ratio < 0.20 THEN '15%-19%'
        ELSE '20%+'
    END AS pti_bucket,
    COUNT(*) AS applications,
    ROUND(AVG(estimated_pd), 4) AS avg_pd,
    ROUND(AVG(expected_loss_amount), 2) AS avg_expected_loss
FROM credit_decisioning_sim.synthetic_applications
GROUP BY 1
ORDER BY 1;

What you want:

  • average PD should generally rise as PTI worsens
  • expected loss should also tend to rise, though exposure size can create noise

This is one of the most important validations in the whole review.

6. Review mixed-signal applications

This is where realism shows up.

The script already gives you three useful spot checks:

  • strong credit + high PTI
  • weaker credit + manageable PTI
  • large exposure + manageable affordability

These are not errors. These are desirable.

What to look for:

Strong credit + high PTI

Ask:

  • does the structure justify the burden?
  • is it often a shorter-term personal loan or similar?
  • does the PD increase, but not explode unrealistically?

Weaker credit + manageable PTI

Ask:

  • does longer term or lower payment structure explain it?
  • does PD remain weaker than prime, but not as bad as score alone would imply?

Large exposure + manageable affordability

Ask:

  • is this mainly mortgage / HELOC?
  • does long amortization or interest-only structure explain it?

If these samples make intuitive sense, your engine is doing real work.

If they look absurd, that points to amount, term, or APR scaling issues.

7. Review PD distribution directly

You already validated average PD by score band and product, but now check the actual spread.

Run:

SELECT
    MIN(estimated_pd) AS min_pd,
    PERCENTILE_CONT(0.10) WITHIN GROUP (ORDER BY estimated_pd) AS p10_pd,
    PERCENTILE_CONT(0.25) WITHIN GROUP (ORDER BY estimated_pd) AS p25_pd,
    PERCENTILE_CONT(0.50) WITHIN GROUP (ORDER BY estimated_pd) AS median_pd,
    PERCENTILE_CONT(0.75) WITHIN GROUP (ORDER BY estimated_pd) AS p75_pd,
    PERCENTILE_CONT(0.90) WITHIN GROUP (ORDER BY estimated_pd) AS p90_pd,
    MAX(estimated_pd) AS max_pd
FROM credit_decisioning_sim.synthetic_applications;

What you want:

  • floor close to your defined minimum
  • upper tail present, but not everybody crowding at the cap
  • a healthy spread, not a narrow cluster

Red flags:

  • too many records at the 45% cap
  • almost all records clustered in a tiny PD range
  • very little separation between middle and tail

If too many hit the cap, your multipliers may be too aggressive in combination.

8. Review expected loss as a business output

Expected loss is where exposure and risk come together.

Ask:

  • which products dominate total expected loss?
  • does that make sense?
  • are large secured products driving dollars while unsecured products drive severity?
  • do high-PD small balances coexist with lower-PD large balances?

Useful query:

SELECT
    product_type,
    COUNT(*) AS applications,
    ROUND(SUM(requested_amount), 2) AS total_requested_amount,
    ROUND(SUM(expected_loss_amount), 2) AS total_expected_loss,
    ROUND(AVG(expected_loss_amount), 2) AS avg_expected_loss
FROM credit_decisioning_sim.synthetic_applications
GROUP BY product_type
ORDER BY total_expected_loss DESC;

What you want:

  • a believable loss story, not just mathematically correct output

9. Check for extreme or awkward edge cases

This is the cleanup pass.

Run targeted checks like:

-- Extremely high PTI
SELECT *
FROM credit_decisioning_sim.synthetic_applications
WHERE payment_to_income_ratio > 0.35
ORDER BY payment_to_income_ratio DESC
LIMIT 25;

-- Very low score but very low PD
SELECT *
FROM credit_decisioning_sim.synthetic_applications

LIMIT 25;

-- Very high score but very high PD
SELECT *
FROM credit_decisioning_sim.synthetic_applications
WHERE credit_score >= 760
ORDER BY estimated_pd DESC
LIMIT 25;

What to ask:

  • do these records make sense when you inspect all fields together?
  • are there any combinations that feel synthetic in a bad way?

You are not trying to eliminate all unusual records. You are trying to eliminate unjustified unusual records.

What “good” looks like overall

If the engine is healthy, you should see:

  • configured product and score mixes approximately honored
  • strong directional worsening from super-prime to deep subprime
  • realistic overlap across borrower characteristics
  • product structures materially affecting payment and PTI
  • PTI clearly influencing PD
  • expected loss telling a believable business story
  • mixed-signal edge cases that feel plausible, not random nonsense

What would trigger revisions

You should consider edits if you see any of these:
