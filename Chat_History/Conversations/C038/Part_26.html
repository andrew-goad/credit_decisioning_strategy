/***************************************************************************************************
SECTION 3 — FAIL-FAST STRATEGY PARAMETER, SOURCE, PRODUCT POLICY, AND REGISTRY GATEKEEPER
****************************************************************************************************

BUSINESS PURPOSE:
    Prevent invalid Module 2 strategy configuration, malformed product policy configuration,
    ambiguous Module 1 source input, or missing campaign-registry linkage from reaching downstream
    decision logic, archive persistence, comparison, QA, or evidence capture.

    Section 3 answers:

        "Is the current Module 2 run configured well enough to proceed into source staging,
         segmentation, rule construction, decisioning, exposure treatment, archive persistence,
         comparison, validation, and executive evidence capture?"

SQL PURPOSE:
    1. Validate active strategy-parameter cardinality.
    2. Validate strategy identity and archive controls.
    3. Validate campaign registry requirement settings.
    4. Validate threshold ranges and threshold ordering.
    5. Validate decision conventions.
    6. Validate Section 6 rule-control parameters.
    7. Validate failed-counteroffer resolution settings.
    8. Validate product policy completeness, supported products, and product threshold ordering.
    9. Validate Module 1 input source table existence, required fields, row count, scenario selection,
       and application_id uniqueness.
    10. Materialize a temporary source-selection scope helper table.
    11. Match the current technical run key to the persistent Module 2 campaign registry.
    12. Produce lightweight setup diagnostics before downstream stages execute.

WHY FAIL FAST:
    A completed strategy run under invalid configuration is more dangerous than a failed run.

    Gatekeepers prevent silent strategy distortion, ambiguous source selection, stale parameter use,
    unsupported product-policy configuration, invalid archive controls, and weak evidence linkage.

WHY REGISTRY MATCHING BELONGS HERE:
    The campaign registry does not define Module 1 lineage or Module 2 strategy behavior.

    It maps technical scenario / strategy identifiers to stable run IDs used for:
        validation-summary traceability,
        executive evidence capture,
        README storytelling,
        comparison grouping,
        and future campaign documentation.

    Matching the current run key early lets Section 16 capture evidence with clean IDs instead of
    relying only on long technical names.

BOUNDARY:
    Section 3 validates configuration and source readiness.

    Section 3 does not:
        consume rows into the main Module 2 staging table,
        assign strategy segments,
        assign rule flags,
        assign preliminary routing,
        calculate approved exposure,
        assign final decision_outcome,
        assign simulated reason codes,
        create latest-run output,
        insert archive rows,
        perform matched comparison,
        or perform full validation QA.

***************************************************************************************************/



/***************************************************************************************************
SECTION 3.1 — STRATEGY PARAMETER CARDINALITY, THRESHOLD, CONVENTION, AND PRODUCT-POLICY VALIDATION
****************************************************************************************************

BUSINESS PURPOSE:
    Confirm that the active strategy parameter card and product policy parameter card are internally
    coherent before any applicant-level logic is built.

SQL PURPOSE:
    Validate:
        active strategy cardinality,
        strategy identity,
        Module 1 input controls,
        archive controls,
        campaign registry requirement flag,
        synthetic estimated-risk thresholds,
        PTI thresholds,
        DTI thresholds,
        borderline diagnostic buffer,
        Section 6 rule-control parameters,
        decision convention controls,
        failed counteroffer resolution,
        product policy cardinality,
        product threshold ordering,
        counteroffer controls,
        approved amount controls,
        and rounding controls.

INTERPRETATION:
    These checks validate the strategy configuration, not the strategy result.

    Passing Section 3.1 means:
        the parameter cards are coherent enough to execute.

    It does not mean:
        final outcomes are reasonable,
        reason codes are complete,
        archive persistence worked,
        or the strategy is validated.

****************************************************************************************************/

DO $$
DECLARE
    p RECORD;

    v_active_strategy_count BIGINT;
    v_product_policy_count BIGINT;
    v_supported_product_count BIGINT;
    v_duplicate_product_count BIGINT;
    v_unsupported_product_count BIGINT;
    v_missing_supported_product_count BIGINT;
    v_bad_product_policy_count BIGINT;
BEGIN
    /*-------------------------------------------------------------------------------------------
    Gatekeeper: exactly one active strategy parameter row.

    Single-strategy execution requires one and only one active strategy configuration.

    If more than one strategy row is active, downstream logic could mix strategy identities,
    thresholds, archive controls, and evidence metadata.
    -------------------------------------------------------------------------------------------*/
    SELECT COUNT(*)
    INTO v_active_strategy_count
    FROM tmp_module2_strategy_params
    WHERE active_strategy_flag IS TRUE;

    IF v_active_strategy_count <> 1 THEN
        RAISE EXCEPTION
            'Module 2 gatekeeper failure: expected exactly one active strategy parameter row, found %.',
            v_active_strategy_count;
    END IF;

    SELECT *
    INTO p
    FROM tmp_module2_strategy_params
    WHERE active_strategy_flag IS TRUE
    LIMIT 1;


    /*-------------------------------------------------------------------------------------------
    Gatekeeper: required strategy identity fields.

    These fields identify the downstream simulated Module 2 strategy, not the upstream Module 1
    scenario.

    Module 1 lineage is validated separately through source selection and source scope.
    -------------------------------------------------------------------------------------------*/
    IF p.module2_model_version IS NULL OR NULLIF(BTRIM(p.module2_model_version), '') IS NULL THEN
        RAISE EXCEPTION 'Module 2 gatekeeper failure: module2_model_version must be non-null and nonblank.';
    END IF;

    IF p.strategy_set_name IS NULL OR NULLIF(BTRIM(p.strategy_set_name), '') IS NULL THEN
        RAISE EXCEPTION 'Module 2 gatekeeper failure: strategy_set_name must be non-null and nonblank.';
    END IF;

    IF p.strategy_name IS NULL OR NULLIF(BTRIM(p.strategy_name), '') IS NULL THEN
        RAISE EXCEPTION 'Module 2 gatekeeper failure: strategy_name must be non-null and nonblank.';
    END IF;

    IF p.strategy_version IS NULL OR NULLIF(BTRIM(p.strategy_version), '') IS NULL THEN
        RAISE EXCEPTION 'Module 2 gatekeeper failure: strategy_version must be non-null and nonblank.';
    END IF;

    IF p.strategy_run_id IS NULL OR NULLIF(BTRIM(p.strategy_run_id), '') IS NULL THEN
        RAISE EXCEPTION 'Module 2 gatekeeper failure: strategy_run_id must be non-null and nonblank.';
    END IF;

    IF p.strategy_run_ts IS NULL THEN
        RAISE EXCEPTION 'Module 2 gatekeeper failure: strategy_run_ts must be non-null.';
    END IF;


    /*-------------------------------------------------------------------------------------------
    Gatekeeper: campaign registry requirement flag.

    campaign_registry_required_flag controls evidence-traceability expectations.

    TRUE:
        the current technical run key should match exactly one active row in
        credit_decisioning_sim.strategy_run_campaign_registry.

    FALSE:
        ad hoc development runs may proceed with fallback story metadata, but formal campaign
        evidence should still be registry matched.

    This flag does not change decision logic.
    -------------------------------------------------------------------------------------------*/
    IF p.campaign_registry_required_flag IS NULL THEN
        RAISE EXCEPTION
            'Module 2 gatekeeper failure: campaign_registry_required_flag must not be null.';
    END IF;


    /*-------------------------------------------------------------------------------------------
    Gatekeeper: Module 1 input source.

    LATEST:
        credit_decisioning_sim.synthetic_applications

    ARCHIVE:
        credit_decisioning_sim.synthetic_applications_scenario_archive

    Multi-scenario processing is not designed in Module 2 V1.0.
    -------------------------------------------------------------------------------------------*/
    IF p.module1_input_source IS NULL
       OR p.module1_input_source NOT IN ('LATEST', 'ARCHIVE') THEN
        RAISE EXCEPTION
            'Module 2 gatekeeper failure: module1_input_source must be LATEST or ARCHIVE. Found: %.',
            COALESCE(p.module1_input_source, '<NULL>');
    END IF;

    IF p.module1_input_source = 'ARCHIVE' THEN
        IF p.source_module1_scenario_set_name IS NULL
           OR NULLIF(BTRIM(p.source_module1_scenario_set_name), '') IS NULL
           OR p.source_module1_scenario_name IS NULL
           OR NULLIF(BTRIM(p.source_module1_scenario_name), '') IS NULL
           OR p.source_population_id IS NULL
           OR NULLIF(BTRIM(p.source_population_id), '') IS NULL THEN
            RAISE EXCEPTION
                'Module 2 gatekeeper failure: ARCHIVE source requires source_module1_scenario_set_name, source_module1_scenario_name, and source_population_id.';
        END IF;
    END IF;


    /*-------------------------------------------------------------------------------------------
    Gatekeeper: archive controls.

    Archive behavior is not handled here. Section 12 performs archive persistence.

    Section 3 only validates that the active strategy has a coherent archive-control configuration.
    -------------------------------------------------------------------------------------------*/
    IF p.archive_run_flag IS NULL THEN
        RAISE EXCEPTION 'Module 2 gatekeeper failure: archive_run_flag must not be null.';
    END IF;

    IF p.strategy_archive_reset_mode IS NULL
       OR p.strategy_archive_reset_mode NOT IN (
            'NONE',
            'STRATEGY_SCENARIO_ONLY',
            'STRATEGY_SET_ONLY',
            'ALL'
       ) THEN
        RAISE EXCEPTION
            'Module 2 gatekeeper failure: strategy_archive_reset_mode must be NONE, STRATEGY_SCENARIO_ONLY, STRATEGY_SET_ONLY, or ALL. Found: %.',
            COALESCE(p.strategy_archive_reset_mode, '<NULL>');
    END IF;


    /*-------------------------------------------------------------------------------------------
    Gatekeeper: synthetic estimated-PD proxy threshold bounds and ordering.

    estimated_pd remains the SQL field name from Module 1.

    In Module 2, these thresholds interpret estimated_pd as the synthetic estimated-PD proxy.

    The gatekeeper validates ordering so that true risk bands remain coherent:
        clean approval band,
        counteroffer band,
        review band,
        decline band.
    -------------------------------------------------------------------------------------------*/
    IF p.approve_max_estimated_pd_proxy IS NULL
       OR p.counteroffer_max_estimated_pd_proxy IS NULL
       OR p.review_max_estimated_pd_proxy IS NULL
       OR p.decline_min_estimated_pd_proxy IS NULL
       OR p.approve_max_estimated_pd_proxy < 0
       OR p.approve_max_estimated_pd_proxy > 1
       OR p.counteroffer_max_estimated_pd_proxy < 0
       OR p.counteroffer_max_estimated_pd_proxy > 1
       OR p.review_max_estimated_pd_proxy < 0
       OR p.review_max_estimated_pd_proxy > 1
       OR p.decline_min_estimated_pd_proxy < 0
       OR p.decline_min_estimated_pd_proxy > 1 THEN
        RAISE EXCEPTION
            'Module 2 gatekeeper failure: synthetic estimated-PD proxy thresholds must be non-null and between 0 and 1.';
    END IF;

    IF NOT (
        p.approve_max_estimated_pd_proxy < p.counteroffer_max_estimated_pd_proxy
        AND p.counteroffer_max_estimated_pd_proxy <= p.review_max_estimated_pd_proxy
        AND p.review_max_estimated_pd_proxy <= p.decline_min_estimated_pd_proxy
    ) THEN
        RAISE EXCEPTION
            'Module 2 gatekeeper failure: synthetic estimated-PD proxy threshold ordering is invalid.';
    END IF;


    /*-------------------------------------------------------------------------------------------
    Gatekeeper: global PTI threshold bounds and ordering.

    PTI thresholds are strategy simulation controls, not production underwriting cutoffs.

    Product-level PTI thresholds govern product-aware affordability flags. Global thresholds provide
    cross-product governance context and range discipline.
    -------------------------------------------------------------------------------------------*/
    IF p.global_approve_max_pti IS NULL
       OR p.global_review_max_pti IS NULL
       OR p.global_decline_min_pti IS NULL
       OR p.global_approve_max_pti < 0
       OR p.global_approve_max_pti > 1.5
       OR p.global_review_max_pti < 0
       OR p.global_review_max_pti > 1.5
       OR p.global_decline_min_pti < 0
       OR p.global_decline_min_pti > 1.5 THEN
        RAISE EXCEPTION
            'Module 2 gatekeeper failure: global PTI thresholds must be non-null and between 0 and 1.5.';
    END IF;

    IF NOT (
        p.global_approve_max_pti < p.global_review_max_pti
        AND p.global_review_max_pti <= p.global_decline_min_pti
    ) THEN
        RAISE EXCEPTION
            'Module 2 gatekeeper failure: global PTI threshold ordering is invalid.';
    END IF;


    /*-------------------------------------------------------------------------------------------
    Gatekeeper: DTI threshold bounds and ordering.

    DTI is an existing-obligation capacity signal.

    Module 2 V1.0 does not directly solve high DTI through exposure reduction because counteroffer
    changes the requested exposure treatment, not the applicant's existing obligations.
    -------------------------------------------------------------------------------------------*/
    IF p.approve_max_dti IS NULL
       OR p.review_max_dti IS NULL
       OR p.decline_min_dti IS NULL
       OR p.approve_max_dti < 0
       OR p.approve_max_dti > 1
       OR p.review_max_dti < 0
       OR p.review_max_dti > 1
       OR p.decline_min_dti < 0
       OR p.decline_min_dti > 1 THEN
        RAISE EXCEPTION
            'Module 2 gatekeeper failure: DTI thresholds must be non-null and between 0 and 1.';
    END IF;

    IF NOT (
        p.approve_max_dti < p.review_max_dti
        AND p.review_max_dti <= p.decline_min_dti
    ) THEN
        RAISE EXCEPTION
            'Module 2 gatekeeper failure: DTI threshold ordering is invalid.';
    END IF;


    /*-------------------------------------------------------------------------------------------
    Gatekeeper: borderline diagnostic buffer.

    This parameter exists only to support non-decisioning segmentation.

    It prevents hidden hardcoded "near threshold" logic from appearing inside downstream CASE blocks.

    Allowed range:
        0.000000 to 0.250000

    Interpretation:
        0.000000 disables threshold-adjacent borderline tagging.
        Values above 0.250000 are not allowed because they would make too much of the population
        appear borderline and reduce diagnostic usefulness.

    Boundary:
        This is not a production policy tolerance.
    -------------------------------------------------------------------------------------------*/
    IF p.borderline_threshold_buffer_pct IS NULL
       OR p.borderline_threshold_buffer_pct < 0
       OR p.borderline_threshold_buffer_pct > 0.250000 THEN
        RAISE EXCEPTION
            'Module 2 gatekeeper failure: borderline_threshold_buffer_pct must be between 0 and 0.25.';
    END IF;


    /*-------------------------------------------------------------------------------------------
    Gatekeeper: Section 6 rule-control parameters.

    These parameters govern simulated rule trigger flags only.

    They do not create:
        final strategy outcomes,
        reason codes,
        approved amounts,
        approved PTI,
        or approved Expected Loss.
    -------------------------------------------------------------------------------------------*/
    IF p.bankruptcy_policy_stop_enabled IS NULL
       OR p.major_derogatory_policy_stop_enabled IS NULL
       OR p.severe_delinquency_policy_stop_enabled IS NULL
       OR p.high_utilization_review_enabled IS NULL
       OR p.low_score_review_enabled IS NULL THEN
        RAISE EXCEPTION
            'Module 2 gatekeeper failure: Section 6 boolean rule-control parameters must not be null.';
    END IF;

    IF p.severe_delinquency_count_threshold IS NULL
       OR p.severe_delinquency_count_threshold < 0 THEN
        RAISE EXCEPTION
            'Module 2 gatekeeper failure: severe_delinquency_count_threshold must be a non-negative integer.';
    END IF;

    IF p.high_utilization_review_threshold IS NULL
       OR p.high_utilization_review_threshold < 0
       OR p.high_utilization_review_threshold > 1 THEN
        RAISE EXCEPTION
            'Module 2 gatekeeper failure: high_utilization_review_threshold must be between 0 and 1.';
    END IF;

    IF p.low_score_review_threshold IS NULL
       OR p.low_score_review_threshold < 300
       OR p.low_score_review_threshold > 850 THEN
        RAISE EXCEPTION
            'Module 2 gatekeeper failure: low_score_review_threshold must be between 300 and 850.';
    END IF;


    /*-------------------------------------------------------------------------------------------
    Gatekeeper: decision convention controls.

    These conventions preserve the accepted Module 2 V1.0 final-output taxonomy:
        APPROVE uses requested exposure,
        COUNTEROFFER uses reduced approved exposure,
        MANUAL_REVIEW remains unresolved,
        DECLINE uses zero-exposure convention.
    -------------------------------------------------------------------------------------------*/
    IF p.allow_approved_amount_above_requested_flag IS DISTINCT FROM FALSE THEN
        RAISE EXCEPTION
            'Module 2 gatekeeper failure: allow_approved_amount_above_requested_flag must be FALSE for Module 2 V1.0.';
    END IF;

    IF p.decline_approved_amount_convention <> 'ZERO' THEN
        RAISE EXCEPTION
            'Module 2 gatekeeper failure: decline_approved_amount_convention must equal ZERO.';
    END IF;

    IF p.manual_review_approved_amount_convention <> 'NULL_UNRESOLVED' THEN
        RAISE EXCEPTION
            'Module 2 gatekeeper failure: manual_review_approved_amount_convention must equal NULL_UNRESOLVED.';
    END IF;

    IF p.approved_el_decline_convention <> 'ZERO' THEN
        RAISE EXCEPTION
            'Module 2 gatekeeper failure: approved_el_decline_convention must equal ZERO.';
    END IF;

    IF p.approved_el_manual_review_convention <> 'NULL_UNRESOLVED' THEN
        RAISE EXCEPTION
            'Module 2 gatekeeper failure: approved_el_manual_review_convention must equal NULL_UNRESOLVED.';
    END IF;

    IF p.reason_code_required_flag IS DISTINCT FROM TRUE THEN
        RAISE EXCEPTION
            'Module 2 gatekeeper failure: reason_code_required_flag must be TRUE.';
    END IF;

    IF p.simulated_offer_exposure_flag_enabled IS DISTINCT FROM TRUE THEN
        RAISE EXCEPTION
            'Module 2 gatekeeper failure: simulated_offer_exposure_flag_enabled must be TRUE.';
    END IF;

    IF p.approve_reason_code IS NULL
       OR NULLIF(BTRIM(p.approve_reason_code), '') IS NULL THEN
        RAISE EXCEPTION
            'Module 2 gatekeeper failure: approve_reason_code must be non-null and nonblank.';
    END IF;


    /*-------------------------------------------------------------------------------------------
    Gatekeeper: failed counteroffer resolution.

    This parameter governs final decision resolution for preliminary COUNTEROFFER rows where
    Section 8 determines that no viable reduced-exposure treatment exists.

    Allowed values:
        MANUAL_REVIEW
        DECLINE

    Default:
        MANUAL_REVIEW

    Boundary:
        This is a simulated strategy-control parameter. It is not production underwriting policy.
    -------------------------------------------------------------------------------------------*/
    IF p.failed_counteroffer_resolution IS NULL
       OR p.failed_counteroffer_resolution NOT IN ('MANUAL_REVIEW', 'DECLINE') THEN
        RAISE EXCEPTION
            'Module 2 gatekeeper failure: failed_counteroffer_resolution must be MANUAL_REVIEW or DECLINE. Found: %.',
            COALESCE(p.failed_counteroffer_resolution, '<NULL>');
    END IF;


    /*-------------------------------------------------------------------------------------------
    Gatekeeper: product policy table contains exactly one row per supported product type.

    Product policy rows are required before product-specific affordability, exposure, Expected Loss,
    counteroffer, and rounding rules can be applied.
    -------------------------------------------------------------------------------------------*/
    SELECT COUNT(*)
    INTO v_product_policy_count
    FROM tmp_module2_product_policy_params;

    SELECT COUNT(DISTINCT product_type)
    INTO v_supported_product_count
    FROM tmp_module2_product_policy_params
    WHERE product_type IN (
        'MORTGAGE',
        'HELOC',
        'AUTO_LOAN',
        'UNSECURED_PERSONAL_LOAN',
        'REVOLVING_LINE'
    );

    SELECT COUNT(*)
    INTO v_duplicate_product_count
    FROM (
        SELECT product_type
        FROM tmp_module2_product_policy_params
        GROUP BY product_type
        HAVING COUNT(*) > 1
    ) d;

    SELECT COUNT(*)
    INTO v_unsupported_product_count
    FROM tmp_module2_product_policy_params
    WHERE product_type NOT IN (
        'MORTGAGE',
        'HELOC',
        'AUTO_LOAN',
        'UNSECURED_PERSONAL_LOAN',
        'REVOLVING_LINE'
    );

    SELECT COUNT(*)
    INTO v_missing_supported_product_count
    FROM (
        SELECT product_type
        FROM (
            VALUES
                ('MORTGAGE'),
                ('HELOC'),
                ('AUTO_LOAN'),
                ('UNSECURED_PERSONAL_LOAN'),
                ('REVOLVING_LINE')
        ) s(product_type)
        EXCEPT
        SELECT product_type
        FROM tmp_module2_product_policy_params
    ) m;

    IF v_product_policy_count <> 5
       OR v_supported_product_count <> 5
       OR v_duplicate_product_count > 0
       OR v_unsupported_product_count > 0
       OR v_missing_supported_product_count > 0 THEN
        RAISE EXCEPTION
            'Module 2 gatekeeper failure: product policy table must contain exactly one row for each supported product type. Rows=%, supported distinct=%, duplicate groups=%, unsupported rows=%, missing supported products=%.',
            v_product_policy_count,
            v_supported_product_count,
            v_duplicate_product_count,
            v_unsupported_product_count,
            v_missing_supported_product_count;
    END IF;


    /*-------------------------------------------------------------------------------------------
    Gatekeeper: product policy threshold and exposure validation.

    This validates that every product row has coherent:
        requested PTI thresholds,
        requested Expected Loss thresholds,
        approved Expected Loss cap,
        approved exposure range,
        counteroffer controls,
        exposure assignment method,
        and rounding increment.
    -------------------------------------------------------------------------------------------*/
    SELECT COUNT(*)
    INTO v_bad_product_policy_count
    FROM tmp_module2_product_policy_params
    WHERE product_type IS NULL
       OR NULLIF(BTRIM(product_type), '') IS NULL

       OR product_approve_max_pti IS NULL
       OR product_review_max_pti IS NULL
       OR product_decline_min_pti IS NULL
       OR counteroffer_target_pti IS NULL
       OR product_approve_max_pti < 0
       OR product_approve_max_pti > 1.5
       OR product_review_max_pti < 0
       OR product_review_max_pti > 1.5
       OR product_decline_min_pti < 0
       OR product_decline_min_pti > 1.5
       OR counteroffer_target_pti < 0
       OR counteroffer_target_pti > 1.5
       OR product_approve_max_pti >= product_review_max_pti
       OR product_review_max_pti > product_decline_min_pti

       OR product_approve_max_requested_el IS NULL
       OR product_review_max_requested_el IS NULL
       OR product_decline_min_requested_el IS NULL
       OR product_approved_el_cap IS NULL
       OR product_approve_max_requested_el < 0
       OR product_review_max_requested_el < 0
       OR product_decline_min_requested_el < 0
       OR product_approved_el_cap < 0
       OR product_approve_max_requested_el > product_review_max_requested_el
       OR product_review_max_requested_el > product_decline_min_requested_el

       OR product_min_approved_amount IS NULL
       OR product_max_approved_amount IS NULL
       OR product_min_approved_amount <= 0
       OR product_max_approved_amount <= product_min_approved_amount

       OR counteroffer_allowed_flag IS NULL
       OR manual_review_allowed_flag IS NULL
       OR product_min_counteroffer_pct IS NULL
       OR product_max_exposure_reduction_pct IS NULL
       OR product_min_counteroffer_pct < 0
       OR product_min_counteroffer_pct > 1
       OR product_max_exposure_reduction_pct < 0
       OR product_max_exposure_reduction_pct > 1
       OR exposure_assignment_method IS NULL
       OR exposure_assignment_method NOT IN ('MOST_CONSERVATIVE_FEASIBLE_AMOUNT')
       OR approved_amount_rounding_increment IS NULL
       OR approved_amount_rounding_increment <= 0;

    IF v_bad_product_policy_count > 0 THEN
        RAISE EXCEPTION
            'Module 2 gatekeeper failure: % product policy row(s) failed threshold, exposure, counteroffer, or rounding validation.',
            v_bad_product_policy_count;
    END IF;
END $$;



/***************************************************************************************************
SECTION 3.2 — MODULE 1 SOURCE-INPUT VALIDATION AND SOURCE-SCOPE MATERIALIZATION
****************************************************************************************************

BUSINESS PURPOSE:
    Validate that the selected Module 1 source exists, contains rows, has required fields, is scoped
    to exactly one scenario / population slice, and has no duplicate application_id values.

SQL PURPOSE:
    1. Determine whether Module 2 is consuming Module 1 LATEST output or ARCHIVE output.
    2. Validate required Module 1 source fields.
    3. Validate scenario lineage fields.
    4. Validate source row count.
    5. Validate one Module 1 scenario / population slice.
    6. Validate application_id uniqueness.
    7. Validate required-field completeness.
    8. Materialize tmp_m2_source_selection_scope for later registry matching and review.

WHY THIS MATTERS:
    Module 2 strategy comparison depends on exact source lineage.

    If source selection is ambiguous, downstream strategy outcomes may be attributed to strategy
    changes when they actually reflect population drift or source-table errors.

SOURCE-SCOPE HELPER:
    tmp_m2_source_selection_scope records the effective Module 1 scenario set, scenario name,
    population_id, source table, selected row count, and selected distinct application count.

    Section 3.3 uses it to match the current run to the campaign registry.

BOUNDARY:
    This section validates source readiness only.
    Section 4 will later create the normalized source staging table.

****************************************************************************************************/

DO $$
DECLARE
    p RECORD;

    v_source_table_schema TEXT;
    v_source_table_name TEXT;
    v_source_regclass REGCLASS;

    v_scenario_set_col TEXT;
    v_scenario_name_col TEXT;

    v_effective_module1_scenario_set_name TEXT;
    v_effective_module1_scenario_name TEXT;
    v_effective_population_id TEXT;

    v_required_missing_columns TEXT;
    v_source_row_count BIGINT;
    v_selected_row_count BIGINT;
    v_selected_distinct_application_count BIGINT;
    v_duplicate_application_group_count BIGINT;
    v_scenario_population_count BIGINT;
    v_null_required_field_count BIGINT;

    v_required_column_list TEXT[] := ARRAY[
        'application_id',
        'applicant_id',
        'product_type',
        'score_band',
        'credit_score',
        'requested_amount',
        'annual_income',
        'monthly_payment_proxy',
        'payment_to_income_ratio',
        'amount_to_income_ratio',
        'debt_to_income_ratio',
        'utilization_rate',
        'tradeline_count',
        'months_since_oldest_trade',
        'recent_inquiry_count',
        'delinquency_count_12m',
        'major_derogatory_flag',
        'bankruptcy_flag',
        'estimated_pd',
        'estimated_lgd',
        'expected_loss_amount',
        'population_id'
    ];

    v_null_check_expression TEXT;
BEGIN
    SELECT *
    INTO p
    FROM tmp_module2_strategy_params
    WHERE active_strategy_flag IS TRUE
    LIMIT 1;

    IF p.module1_input_source = 'LATEST' THEN
        v_source_table_schema := 'credit_decisioning_sim';
        v_source_table_name := 'synthetic_applications';
    ELSE
        v_source_table_schema := 'credit_decisioning_sim';
        v_source_table_name := 'synthetic_applications_scenario_archive';
    END IF;

    v_source_regclass := TO_REGCLASS(v_source_table_schema || '.' || v_source_table_name);

    IF v_source_regclass IS NULL THEN
        RAISE EXCEPTION
            'Module 2 source-input gatekeeper failure: selected Module 1 source table %.% does not exist.',
            v_source_table_schema,
            v_source_table_name;
    END IF;


    /*-------------------------------------------------------------------------------------------
    Gatekeeper: required Module 1 source fields must be present.

    scenario_set_name / scenario_name may appear either as Module 1 raw names or already-normalized
    Module 2 lineage names. Section 4 aliases them to:
        module1_scenario_set_name
        module1_scenario_name
    -------------------------------------------------------------------------------------------*/
    SELECT STRING_AGG(missing_col, ', ' ORDER BY missing_col)
    INTO v_required_missing_columns
    FROM (
        SELECT unnest(v_required_column_list) AS missing_col
        EXCEPT
        SELECT column_name
        FROM information_schema.columns
        WHERE table_schema = v_source_table_schema
          AND table_name = v_source_table_name
    ) m;

    IF v_required_missing_columns IS NOT NULL THEN
        RAISE EXCEPTION
            'Module 2 source-input gatekeeper failure: selected Module 1 source %.% is missing required field(s): %.',
            v_source_table_schema,
            v_source_table_name,
            v_required_missing_columns;
    END IF;

    IF EXISTS (
        SELECT 1
        FROM information_schema.columns
        WHERE table_schema = v_source_table_schema
          AND table_name = v_source_table_name
          AND column_name = 'module1_scenario_set_name'
    ) THEN
        v_scenario_set_col := 'module1_scenario_set_name';
    ELSIF EXISTS (
        SELECT 1
        FROM information_schema.columns
        WHERE table_schema = v_source_table_schema
          AND table_name = v_source_table_name
          AND column_name = 'scenario_set_name'
    ) THEN
        v_scenario_set_col := 'scenario_set_name';
    ELSE
        RAISE EXCEPTION
            'Module 2 source-input gatekeeper failure: selected Module 1 source %.% must contain scenario_set_name or module1_scenario_set_name.',
            v_source_table_schema,
            v_source_table_name;
    END IF;

    IF EXISTS (
        SELECT 1
        FROM information_schema.columns
        WHERE table_schema = v_source_table_schema
          AND table_name = v_source_table_name
          AND column_name = 'module1_scenario_name'
    ) THEN
        v_scenario_name_col := 'module1_scenario_name';
    ELSIF EXISTS (
        SELECT 1
        FROM information_schema.columns
        WHERE table_schema = v_source_table_schema
          AND table_name = v_source_table_name
          AND column_name = 'scenario_name'
    ) THEN
        v_scenario_name_col := 'scenario_name';
    ELSE
        RAISE EXCEPTION
            'Module 2 source-input gatekeeper failure: selected Module 1 source %.% must contain scenario_name or module1_scenario_name.',
            v_source_table_schema,
            v_source_table_name;
    END IF;


    /*-------------------------------------------------------------------------------------------
    Gatekeeper: selected source table must contain rows.
    -------------------------------------------------------------------------------------------*/
    EXECUTE FORMAT(
        'SELECT COUNT(*) FROM %I.%I',
        v_source_table_schema,
        v_source_table_name
    )
    INTO v_source_row_count;

    IF v_source_row_count = 0 THEN
        RAISE EXCEPTION
            'Module 2 source-input gatekeeper failure: selected Module 1 source %.% contains zero rows.',
            v_source_table_schema,
            v_source_table_name;
    END IF;


    /*-------------------------------------------------------------------------------------------
    Gatekeeper: selected latest-run or archive slice must contain exactly one scenario / population.

    LATEST:
        latest-run table must already represent exactly one Module 1 scenario / population.

    ARCHIVE:
        Section 3 filters using the selected source scenario fields and population_id.
    -------------------------------------------------------------------------------------------*/
    IF p.module1_input_source = 'LATEST' THEN
        EXECUTE FORMAT(
            'SELECT COUNT(*) FROM (
                 SELECT DISTINCT %I, %I, population_id
                 FROM %I.%I
             ) s',
            v_scenario_set_col,
            v_scenario_name_col,
            v_source_table_schema,
            v_source_table_name
        )
        INTO v_scenario_population_count;

        IF v_scenario_population_count <> 1 THEN
            RAISE EXCEPTION
                'Module 2 source-input gatekeeper failure: latest-run Module 1 source contains % scenario / population combinations. Module 2 V1.0 expects exactly one.',
                v_scenario_population_count;
        END IF;

        EXECUTE FORMAT(
            'SELECT %I::TEXT, %I::TEXT, population_id::TEXT
             FROM %I.%I
             LIMIT 1',
            v_scenario_set_col,
            v_scenario_name_col,
            v_source_table_schema,
            v_source_table_name
        )
        INTO
            v_effective_module1_scenario_set_name,
            v_effective_module1_scenario_name,
            v_effective_population_id;

        EXECUTE FORMAT(
            'SELECT COUNT(*), COUNT(DISTINCT application_id)
             FROM %I.%I',
            v_source_table_schema,
            v_source_table_name
        )
        INTO v_selected_row_count, v_selected_distinct_application_count;

        EXECUTE FORMAT(
            'SELECT COUNT(*) FROM (
                 SELECT application_id
                 FROM %I.%I
                 GROUP BY application_id
                 HAVING COUNT(*) > 1
             ) d',
            v_source_table_schema,
            v_source_table_name
        )
        INTO v_duplicate_application_group_count;

        v_null_check_expression :=
            'application_id IS NULL
             OR applicant_id IS NULL
             OR product_type IS NULL
             OR score_band IS NULL
             OR credit_score IS NULL
             OR requested_amount IS NULL
             OR annual_income IS NULL
             OR monthly_payment_proxy IS NULL
             OR payment_to_income_ratio IS NULL
             OR amount_to_income_ratio IS NULL
             OR debt_to_income_ratio IS NULL
             OR utilization_rate IS NULL
             OR tradeline_count IS NULL
             OR months_since_oldest_trade IS NULL
             OR recent_inquiry_count IS NULL
             OR delinquency_count_12m IS NULL
             OR major_derogatory_flag IS NULL
             OR bankruptcy_flag IS NULL
             OR estimated_pd IS NULL
             OR estimated_lgd IS NULL
             OR expected_loss_amount IS NULL
             OR population_id IS NULL
             OR ' || FORMAT('%I IS NULL', v_scenario_set_col) || '
             OR ' || FORMAT('%I IS NULL', v_scenario_name_col);

        EXECUTE FORMAT(
            'SELECT COUNT(*)
             FROM %I.%I
             WHERE %s',
            v_source_table_schema,
            v_source_table_name,
            v_null_check_expression
        )
        INTO v_null_required_field_count;

    ELSE
        v_effective_module1_scenario_set_name := p.source_module1_scenario_set_name;
        v_effective_module1_scenario_name := p.source_module1_scenario_name;
        v_effective_population_id := p.source_population_id;

        EXECUTE FORMAT(
            'SELECT COUNT(*) FROM %I.%I
             WHERE %I = $1
               AND %I = $2
               AND population_id = $3',
            v_source_table_schema,
            v_source_table_name,
            v_scenario_set_col,
            v_scenario_name_col
        )
        INTO v_selected_row_count
        USING
            p.source_module1_scenario_set_name,
            p.source_module1_scenario_name,
            p.source_population_id;

        IF v_selected_row_count = 0 THEN
            RAISE EXCEPTION
                'Module 2 source-input gatekeeper failure: selected Module 1 archive slice contains zero rows. scenario_set=%, scenario_name=%, population_id=%.',
                p.source_module1_scenario_set_name,
                p.source_module1_scenario_name,
                p.source_population_id;
        END IF;

        EXECUTE FORMAT(
            'SELECT COUNT(*) FROM (
                 SELECT DISTINCT %I, %I, population_id
                 FROM %I.%I
                 WHERE %I = $1
                   AND %I = $2
                   AND population_id = $3
             ) s',
            v_scenario_set_col,
            v_scenario_name_col,
            v_source_table_schema,
            v_source_table_name,
            v_scenario_set_col,
            v_scenario_name_col
        )
        INTO v_scenario_population_count
        USING
            p.source_module1_scenario_set_name,
            p.source_module1_scenario_name,
            p.source_population_id;

        IF v_scenario_population_count <> 1 THEN
            RAISE EXCEPTION
                'Module 2 source-input gatekeeper failure: selected Module 1 archive slice contains % scenario / population combinations. Expected exactly one.',
                v_scenario_population_count;
        END IF;

        EXECUTE FORMAT(
            'SELECT COUNT(DISTINCT application_id)
             FROM %I.%I
             WHERE %I = $1
               AND %I = $2
               AND population_id = $3',
            v_source_table_schema,
            v_source_table_name,
            v_scenario_set_col,
            v_scenario_name_col
        )
        INTO v_selected_distinct_application_count
        USING
            p.source_module1_scenario_set_name,
            p.source_module1_scenario_name,
            p.source_population_id;

        EXECUTE FORMAT(
            'SELECT COUNT(*) FROM (
                 SELECT application_id
                 FROM %I.%I
                 WHERE %I = $1
                   AND %I = $2
                   AND population_id = $3
                 GROUP BY application_id
                 HAVING COUNT(*) > 1
             ) d',
            v_source_table_schema,
            v_source_table_name,
            v_scenario_set_col,
            v_scenario_name_col
        )
        INTO v_duplicate_application_group_count
        USING
            p.source_module1_scenario_set_name,
            p.source_module1_scenario_name,
            p.source_population_id;

        v_null_check_expression :=
            'application_id IS NULL
             OR applicant_id IS NULL
             OR product_type IS NULL
             OR score_band IS NULL
             OR credit_score IS NULL
             OR requested_amount IS NULL
             OR annual_income IS NULL
             OR monthly_payment_proxy IS NULL
             OR payment_to_income_ratio IS NULL
             OR amount_to_income_ratio IS NULL
             OR debt_to_income_ratio IS NULL
             OR utilization_rate IS NULL
             OR tradeline_count IS NULL
             OR months_since_oldest_trade IS NULL
             OR recent_inquiry_count IS NULL
             OR delinquency_count_12m IS NULL
             OR major_derogatory_flag IS NULL
             OR bankruptcy_flag IS NULL
             OR estimated_pd IS NULL
             OR estimated_lgd IS NULL
             OR expected_loss_amount IS NULL
             OR population_id IS NULL
             OR ' || FORMAT('%I IS NULL', v_scenario_set_col) || '
             OR ' || FORMAT('%I IS NULL', v_scenario_name_col);

        EXECUTE FORMAT(
            'SELECT COUNT(*)
             FROM %I.%I
             WHERE %I = $1
               AND %I = $2
               AND population_id = $3
               AND (%s)',
            v_source_table_schema,
            v_source_table_name,
            v_scenario_set_col,
            v_scenario_name_col,
            v_null_check_expression
        )
        INTO v_null_required_field_count
        USING
            p.source_module1_scenario_set_name,
            p.source_module1_scenario_name,
            p.source_population_id;
    END IF;


    IF v_selected_row_count = 0 THEN
        RAISE EXCEPTION
            'Module 2 source-input gatekeeper failure: selected Module 1 source slice contains zero rows.';
    END IF;

    IF v_selected_distinct_application_count <> v_selected_row_count THEN
        RAISE EXCEPTION
            'Module 2 source-input gatekeeper failure: selected Module 1 source slice has duplicate application_id values. Rows=%, distinct application_id=%, duplicate groups=%.',
            v_selected_row_count,
            v_selected_distinct_application_count,
            v_duplicate_application_group_count;
    END IF;

    IF v_duplicate_application_group_count > 0 THEN
        RAISE EXCEPTION
            'Module 2 source-input gatekeeper failure: selected Module 1 source slice contains % duplicate application_id group(s).',
            v_duplicate_application_group_count;

/*-----------------------------------------------------------------------------------------------
3.3B Current run registry match materialization.

This table is intentionally temporary. It records the registry match status for the current execution
and is consumed later by Section 16 evidence capture.

DROP TABLE IF EXISTS tmp_m2_campaign_registry_current_run_match;

CREATE TEMP TABLE tmp_m2_campaign_registry_current_run_match
ON COMMIT PRESERVE ROWS
AS
WITH p AS (
    SELECT *
    FROM tmp_module2_strategy_params
    WHERE active_strategy_flag IS TRUE
    LIMIT 1
),

s AS (
    SELECT *
    FROM tmp_m2_source_selection_scope
    LIMIT 1
),

registry_matches AS (
    SELECT
        r.*
    FROM credit_decisioning_sim.strategy_run_campaign_registry r
    JOIN p
        ON r.strategy_set_name = p.strategy_set_name
       AND r.strategy_name = p.strategy_name
       AND r.strategy_version = p.strategy_version
    JOIN s
        ON r.module1_scenario_set_name = s.effective_module1_scenario_set_name
       AND r.module1_scenario_name = s.effective_module1_scenario_name
       AND r.population_id = s.effective_population_id
    WHERE r.registry_active_flag IS TRUE
),

match_summary AS (
    SELECT
        COUNT(*) AS registry_match_count
    FROM registry_matches
)

SELECT
    p.campaign_registry_required_flag,

    p.module2_model_version,
    p.strategy_set_name,
    p.strategy_name,
    p.strategy_version,
    p.strategy_run_id,
    p.strategy_run_ts,

    s.module1_input_source,
    s.source_table_schema,
    s.source_table_name,
    s.effective_module1_scenario_set_name AS module1_scenario_set_name,
    s.effective_module1_scenario_name AS module1_scenario_name,
    s.effective_population_id AS population_id,

    ms.registry_match_count,

    CASE
        WHEN ms.registry_match_count = 1
            THEN 'RUN_REGISTRY_MATCHED'

        WHEN ms.registry_match_count = 0
         AND p.campaign_registry_required_flag IS TRUE
            THEN 'RUN_REGISTRY_NOT_FOUND_REQUIRED_REVIEW'

        WHEN ms.registry_match_count = 0
         AND p.campaign_registry_required_flag IS FALSE
            THEN 'RUN_REGISTRY_NOT_FOUND_FALLBACK_ALLOWED'

        WHEN ms.registry_match_count > 1
            THEN 'RUN_REGISTRY_DUPLICATE_MATCH_REVIEW_REQUIRED'

        ELSE 'RUN_REGISTRY_MATCH_STATUS_UNKNOWN'
    END AS run_registry_match_status,

    r.module1_run_id,
    r.module2_run_id,
    r.run_sequence_number,

    r.showcase_id,
    r.showcase_name,
    r.comparison_group_id,
    r.validation_evidence_group_id,

    r.module1_parameter_family_changed,
    r.module1_parameter_change_summary,
    r.module2_strategy_family_changed,
    r.module2_parameter_change_summary,

    r.expected_storyline,
    r.validation_summary_section_hint,
    r.readme_storyline_label,
    r.linkedin_post_sequence,

    r.registry_active_flag,
    r.registry_created_ts,
    r.registry_updated_ts

FROM p
CROSS JOIN s
CROSS JOIN match_summary ms
LEFT JOIN registry_matches r
    ON ms.registry_match_count = 1;

/***************************************************************************************************
SECTION 3.4 — THRESHOLD EQUALITY CONVENTION DOCUMENTATION
****************************************************************************************************

PURPOSE:
    Document the equality conventions that downstream Section 5, Section 6, Section 7, Section 8,
    and Section 9 depend on.

WHY THIS MATTERS:
    Boundary conditions can materially change strategy outcomes.

    For example:
        estimated_pd = decline_min_estimated_pd_proxy
    should route consistently as severe synthetic estimated-risk decline trigger.

    Documenting equality conventions prevents later strategy tuning from accidentally changing band
    coverage and route assignment.

SYNTHETIC ESTIMATED-PD PROXY:
    APPROVE eligibility:
        estimated_pd <= approve_max_estimated_pd_proxy

    COUNTEROFFER eligibility:
        estimated_pd > approve_max_estimated_pd_proxy
        AND estimated_pd <= counteroffer_max_estimated_pd_proxy

    MANUAL_REVIEW synthetic risk band:
        estimated_pd > counteroffer_max_estimated_pd_proxy
        AND estimated_pd < decline_min_estimated_pd_proxy

    DECLINE trigger:
        estimated_pd >= decline_min_estimated_pd_proxy

REQUESTED PTI:
    APPROVE:
        requested_payment_to_income_ratio <= product_approve_max_pti

    COUNTEROFFER candidate:
        requested_payment_to_income_ratio > product_approve_max_pti
        and counteroffer can potentially reduce approved PTI to target

    MANUAL_REVIEW:
        requested_payment_to_income_ratio > product_approve_max_pti
        and requested_payment_to_income_ratio < product_decline_min_pti
        where counteroffer is not cleanly viable or review triggers apply

    DECLINE trigger:
        requested_payment_to_income_ratio >= product_decline_min_pti
        when no viable counteroffer or review path is intended

DTI:
    APPROVE:
        debt_to_income_ratio <= approve_max_dti

    MANUAL_REVIEW:
        debt_to_income_ratio > approve_max_dti
        AND debt_to_income_ratio < decline_min_dti

    DECLINE:
        debt_to_income_ratio >= decline_min_dti

REQUESTED EXPECTED LOSS:
    Clean approval must satisfy:
        requested_expected_loss_amount <= product_approve_max_requested_el

    Counteroffer may be considered when requested Expected Loss exceeds clean approval tolerance
    but approved-exposure Expected Loss can satisfy product_approved_el_cap.

    Decline / review boundary uses:
        product_review_max_requested_el
        product_decline_min_requested_el
        final strategy hierarchy

COUNTEROFFER:
    A preliminary counteroffer route is not final.
    Feasibility requires later approved-exposure calculation.

MANUAL REVIEW:
    Manual review remains unresolved by design.

BOUNDARY:
    This section is documentation only.
    It does not execute logic.
    It does not change thresholds.
    It does not change final outcomes.

***************************************************************************************************/

        auditability,
        QA,
        troubleshooting,
        strategy tuning,
        and documentation traceability.

WHY THRESHOLD VALUES ARE ATTACHED:
    Downstream stages should be interpretable without forcing reviewers to reverse-engineer the
    active strategy parameter tables.

    Section 5 therefore carries forward:
        global synthetic estimated-risk thresholds,
        global PTI thresholds,
        DTI thresholds,
        rule-control parameters,
        product PTI thresholds,
        requested Expected Loss thresholds,
        approved Expected Loss caps,
        approved amount limits,
        counteroffer controls,
        and rounding controls.

    This makes later rule flags, preliminary routing, exposure treatment, and final decision resolution
    easier to audit.

ESTIMATED_PD BOUNDARY:
    estimated_pd remains the finalized Module 1 SQL field.

    Section 5 uses estimated_pd only as the synthetic estimated-PD proxy input for diagnostic
    segmentation.

    Section 5 does not recalculate estimated_pd.
    Section 5 does not create a new post-decision risk model.

REQUESTED PTI BOUNDARY:
    requested_payment_to_income_ratio is the original requested-structure PTI from Module 1.

    Approved payment and approved PTI do not exist yet.

    Section 5 therefore segments requested affordability pressure, not approved affordability after
    exposure treatment.

DTI BOUNDARY:
    debt_to_income_ratio is an existing-obligation capacity signal.

    In Module 2 V1.0, DTI is not directly fixed by counteroffer exposure reduction because a
    counteroffer changes the requested exposure treatment, not the applicant's existing obligations.

REQUESTED EXPOSURE VS APPROVED EXPOSURE:
    requested_amount is the original requested exposure from Module 1.

    approved_amount does not exist in Section 5.

    Section 5 may describe requested exposure intensity, but it does not assign approved exposure.

REQUESTED EXPECTED LOSS VS APPROVED EXPECTED LOSS:
    requested_expected_loss_amount is requested-exposure Expected Loss carried from Module 1.

    approved_expected_loss_amount does not exist in Section 5.

    Section 5 segments requested-exposure Expected Loss pressure before any approved-exposure
    treatment is calculated.

MIXED-SIGNAL PROFILE BOUNDARY:
    mixed_signal_profile_type is diagnostic only.

    It identifies realistic overlap patterns such as:
        strong credit with high requested PTI,
        weak credit with low requested PTI,
        large exposure with low synthetic estimated-risk,
        high synthetic estimated-risk with low exposure,
        high DTI with low requested PTI.

    It does not automatically approve, decline, route to review, or trigger counteroffer.

BORDERLINE PROFILE BOUNDARY:
    borderline_profile_flag uses the governed borderline_threshold_buffer_pct parameter from Section 2.

    No hidden hardcoded threshold-adjacent buffer is used.

    Borderline status is diagnostic only. It helps later QA and manual-review trigger interpretation
    but does not create a final outcome in Section 5.

WHY NO DECISION OUTPUTS ARE CREATED IN SECTION 5:
    Section 5 does not create:
        decision_outcome
        decision_path
        approval_flag
        decline_flag
        manual_review_flag
        counteroffer_flag
        simulated_offer_exposure_flag
        reason codes
        approved_amount
        approved payment
        approved PTI
        approved Expected Loss

GOVERNANCE ROLE:
    Section 5 makes the strategy-rule input profile transparent.

    It demonstrates separation of concerns:
        Module 1 source values are preserved.
        Strategy thresholds are attached.
        Diagnostic segments are created.
        Decision logic remains deferred.

COMMON MISUSE TO AVOID:
    Do not interpret strategy_risk_tier as a final decision.
    Do not interpret requested_pti_bucket as approved affordability.
    Do not interpret requested_expected_loss_tier as approved Expected Loss.
    Do not interpret mixed_signal_profile_type as a final route.
    Do not interpret borderline_profile_flag as automatic manual review.
    Do not treat segmentation output as operational applicant treatment.

TESTING RELEVANCE:
    Section 5 local diagnostics help confirm that diagnostic segmentation is complete, stable, and
    aligned to the selected Module 1 population and Module 2 strategy before rule-trigger construction
    begins.

DOWNSTREAM DEPENDENCY:
    Section 6 consumes tmp_m2_stage_2_strategy_segments.

    Downstream rule logic should not read directly from Section 4 when Section 5-derived diagnostic
    fields are needed.

PORTFOLIO ARTIFACT VALUE:
    This section shows that the strategy engine is not a monolithic decision CASE block.

    It demonstrates a mature staged architecture where applicant description, rule triggers,
    preliminary routing, exposure treatment, final outcomes, explanation codes, archive comparison,
    and validation evidence are separated and reviewable.

***************************************************************************************************/

WITH active_strategy_params AS (

    LIMIT 1
),

threshold_enriched AS (
    SELECT
        s.*,

        /*******************************************************************************************
        Global synthetic estimated-risk thresholds.

        estimated_pd is interpreted as the synthetic estimated-PD proxy.
        These thresholds describe synthetic risk bands used for strategy simulation.
        *******************************************************************************************/

        p.counteroffer_max_estimated_pd_proxy,
        p.review_max_estimated_pd_proxy,
        p.decline_min_estimated_pd_proxy,

        /*******************************************************************************************
        Global PTI thresholds.

        Product-specific PTI thresholds are used for product-aware segmentation, but global values
        are retained for strategy transparency.
        *******************************************************************************************/
        p.global_approve_max_pti,
        p.global_review_max_pti,
        p.global_decline_min_pti,

        DTI thresholds.

        DTI remains an existing-obligation capacity signal.
        *******************************************************************************************/

        p.review_max_dti,
        p.decline_min_dti,

        /*******************************************************************************************
        Borderline diagnostic buffer.

        This governed parameter prevents hidden hardcoded threshold-adjacent logic.
        *******************************************************************************************/
        p.borderline_threshold_buffer_pct,

        /*******************************************************************************************
        Section 6 rule-control parameters.

        These are carried forward so rule-trigger logic is transparent in the staged data.
        They do not assign final decisions in Section 5.
        *******************************************************************************************/
        p.bankruptcy_policy_stop_enabled,
        p.major_derogatory_policy_stop_enabled,
        p.severe_delinquency_policy_stop_enabled,
        p.severe_delinquency_count_threshold,
        p.high_utilization_review_enabled,
        p.high_utilization_review_threshold,
        p.low_score_review_enabled,
        p.low_score_review_threshold,

        /*******************************************************************************************
        Product policy thresholds and controls.

        These are attached here for downstream transparency.
        Section 5 does not apply final exposure treatment or counteroffer feasibility logic.
        *******************************************************************************************/
        pp.product_approve_max_pti,
        pp.product_review_max_pti,
        pp.product_decline_min_pti,
        pp.counteroffer_target_pti,

        pp.product_approve_max_requested_el,
        pp.product_review_max_requested_el,
        pp.product_decline_min_requested_el,
        pp.product_approved_el_cap,

        pp.product_min_approved_amount,
        pp.product_max_approved_amount,

        pp.counteroffer_allowed_flag,
        pp.manual_review_allowed_flag,
        pp.product_min_counteroffer_pct,
        pp.product_max_exposure_reduction_pct,
        pp.exposure_assignment_method,
        pp.approved_amount_rounding_increment,

        /*******************************************************************************************
        Requested Expected Loss low / moderate split.

        This uses product_approve_max_requested_el / 2.0 because Section 5 classifies
        requested-exposure Expected Loss.

        product_approved_el_cap is carried forward for later approved-exposure logic but does not
        drive pre-decision requested Expected Loss tiering.
        *******************************************************************************************/
        (pp.product_approve_max_requested_el / 2.0) AS requested_el_low_moderate_split

    FROM tmp_m2_stage_1_source_applications s
    JOIN active_strategy_params p
        ON TRUE
    JOIN tmp_module2_product_policy_params pp
        ON pp.product_type = s.product_type_policy_key
),

score_normalized AS (
    SELECT
        te.*,

        /*******************************************************************************************
        score_band_policy_key.

        Preserve original score_band and create a normalized strategy policy key.

        Module 1 is not modified.
        *******************************************************************************************/
        CASE
            WHEN UPPER(REGEXP_REPLACE(BTRIM(te.score_band::TEXT), '[^A-Za-z0-9]+', '_', 'g'))
                 IN ('SUPER_PRIME', 'SUPERPRIME', 'SP')
                THEN 'SUPER_PRIME'

            WHEN UPPER(REGEXP_REPLACE(BTRIM(te.score_band::TEXT), '[^A-Za-z0-9]+', '_', 'g'))
                 IN ('PRIME', 'P')
                THEN 'PRIME'

            WHEN UPPER(REGEXP_REPLACE(BTRIM(te.score_band::TEXT), '[^A-Za-z0-9]+', '_', 'g'))
                 IN ('NEAR_PRIME', 'NEARPRIME', 'NP')
                THEN 'NEAR_PRIME'

            WHEN UPPER(REGEXP_REPLACE(BTRIM(te.score_band::TEXT), '[^A-Za-z0-9]+', '_', 'g'))
                 IN ('SUBPRIME', 'SUB_PRIME', 'SUB')
                THEN 'SUBPRIME'

            WHEN UPPER(REGEXP_REPLACE(BTRIM(te.score_band::TEXT), '[^A-Za-z0-9]+', '_', 'g'))
                 IN ('DEEP_SUBPRIME', 'DEEP_SUB_PRIME', 'DEEP_SUB', 'DS')
                THEN 'DEEP_SUBPRIME'

            ELSE NULL
        END AS score_band_policy_key

    FROM threshold_enriched te
),

core_segments AS (
    SELECT
        sn.*,

        /*******************************************************************************************
        Synthetic estimated-risk tier.

        Uses estimated_pd as the Module 1 synthetic estimated-PD proxy input.

        Equality handling:
            estimated_pd <= approve_max_estimated_pd_proxy / 2.0
                LOW_SYNTHETIC_RISK

            estimated_pd <= approve_max_estimated_pd_proxy
                MODERATE_SYNTHETIC_RISK

            estimated_pd <= counteroffer_max_estimated_pd_proxy
                ELEVATED_SYNTHETIC_RISK

            estimated_pd < decline_min_estimated_pd_proxy
                HIGH_SYNTHETIC_RISK

            estimated_pd >= decline_min_estimated_pd_proxy
                SEVERE_SYNTHETIC_RISK
        *******************************************************************************************/
        CASE
            WHEN sn.estimated_pd <= (sn.approve_max_estimated_pd_proxy / 2.0)
                THEN 'LOW_SYNTHETIC_RISK'

            WHEN sn.estimated_pd <= sn.approve_max_estimated_pd_proxy
                THEN 'MODERATE_SYNTHETIC_RISK'

            WHEN sn.estimated_pd <= sn.counteroffer_max_estimated_pd_proxy
                THEN 'ELEVATED_SYNTHETIC_RISK'

            WHEN sn.estimated_pd < sn.decline_min_estimated_pd_proxy
                THEN 'HIGH_SYNTHETIC_RISK'

            ELSE 'SEVERE_SYNTHETIC_RISK'
        END AS strategy_risk_tier,


        /*******************************************************************************************
        Requested PTI bucket.

        Uses requested_payment_to_income_ratio from the original Module 1 requested structure.

        Product-specific PTI thresholds are used so affordability segmentation remains product-aware.
        Approved PTI does not exist yet.
        *******************************************************************************************/
        CASE
            WHEN sn.requested_payment_to_income_ratio <= sn.counteroffer_target_pti
                THEN 'LOW_REQUESTED_PTI'

            WHEN sn.requested_payment_to_income_ratio <= sn.product_approve_max_pti
                THEN 'MODERATE_REQUESTED_PTI'

            WHEN sn.requested_payment_to_income_ratio <= sn.product_review_max_pti
                THEN 'ELEVATED_REQUESTED_PTI'

            WHEN sn.requested_payment_to_income_ratio < sn.product_decline_min_pti
                THEN 'HIGH_REQUESTED_PTI'

            ELSE 'SEVERE_REQUESTED_PTI'
        END AS requested_pti_bucket,


        /*******************************************************************************************
        DTI bucket.

        DTI is an existing-obligation capacity signal.

        It is not directly fixed by counteroffer in Module 2 V1.0.
        *******************************************************************************************/
        CASE
            WHEN sn.debt_to_income_ratio <= (sn.approve_max_dti / 2.0)
                THEN 'LOW_DTI'

            WHEN sn.debt_to_income_ratio <= sn.approve_max_dti
                THEN 'MODERATE_DTI'

            WHEN sn.debt_to_income_ratio < sn.review_max_dti
                THEN 'ELEVATED_DTI'

            WHEN sn.debt_to_income_ratio < sn.decline_min_dti
                THEN 'HIGH_DTI'

            ELSE 'SEVERE_DTI'
        END AS dti_bucket,


        /*******************************************************************************************
        Requested exposure tier.

        BELOW_PRODUCT_MINIMUM:
            requested_amount < product_min_approved_amount

        WITHIN_PRODUCT_LIMITS:
            requested_amount is within product minimum and product maximum.

        ABOVE_PRODUCT_APPROVAL_CAP:
            requested_amount exceeds the product maximum, but the product cap can still satisfy the
            governed minimum viable amount after allowed exposure reduction.

        EXTREME_REQUESTED_EXPOSURE:
            requested_amount exceeds the product cap by more than the allowed exposure-reduction
            framework can reasonably address.

        No undocumented magic number is used. The reducibility test uses governed parameters:
            product_min_approved_amount
            product_min_counteroffer_pct
            product_max_exposure_reduction_pct
        *******************************************************************************************/
        CASE
            WHEN sn.requested_amount < sn.product_min_approved_amount
                THEN 'BELOW_PRODUCT_MINIMUM'

            WHEN sn.requested_amount <= sn.product_max_approved_amount
                THEN 'WITHIN_PRODUCT_LIMITS'

            WHEN sn.product_max_approved_amount >= GREATEST(
                    sn.product_min_approved_amount,
                    sn.requested_amount * sn.product_min_counteroffer_pct,
                    sn.requested_amount * (1.0 - sn.product_max_exposure_reduction_pct)
                 )
                THEN 'ABOVE_PRODUCT_APPROVAL_CAP'

            ELSE 'EXTREME_REQUESTED_EXPOSURE'
        END AS requested_exposure_tier,


        /*******************************************************************************************
        Requested Expected Loss tier.

        Uses requested_expected_loss_amount and requested-exposure thresholds.

        product_approved_el_cap is not used for this pre-decision requested Expected Loss tier.
        *******************************************************************************************/
        CASE
            WHEN sn.requested_expected_loss_amount <= sn.requested_el_low_moderate_split
                THEN 'LOW_REQUESTED_EL'

            WHEN sn.requested_expected_loss_amount <= sn.product_approve_max_requested_el
                THEN 'MODERATE_REQUESTED_EL'

            WHEN sn.requested_expected_loss_amount <= sn.product_review_max_requested_el
                THEN 'ELEVATED_REQUESTED_EL'

            WHEN sn.requested_expected_loss_amount < sn.product_decline_min_requested_el
                THEN 'HIGH_REQUESTED_EL'

            ELSE 'SEVERE_REQUESTED_EL'
        END AS requested_expected_loss_tier

    FROM score_normalized sn
),

mixed_signal_conditions AS (
    SELECT
        cs.*,

        /*******************************************************************************************
        Mixed-signal diagnostic conditions.

        These conditions identify realistic strategy QA profiles.

        They do not assign final decisions.
        They do not assign reason codes.
        They do not create rule-trigger flags yet.
        *******************************************************************************************/
        (
            cs.score_band_policy_key IN ('SUPER_PRIME', 'PRIME')
            AND cs.requested_pti_bucket IN ('HIGH_REQUESTED_PTI', 'SEVERE_REQUESTED_PTI')
        ) AS strong_credit_high_pti_condition,

        (
            cs.score_band_policy_key IN ('SUBPRIME', 'DEEP_SUBPRIME')
            AND cs.requested_pti_bucket IN ('LOW_REQUESTED_PTI', 'MODERATE_REQUESTED_PTI')
        ) AS weak_credit_low_pti_condition,

        (
            cs.requested_exposure_tier IN ('ABOVE_PRODUCT_APPROVAL_CAP', 'EXTREME_REQUESTED_EXPOSURE')
            AND cs.strategy_risk_tier IN ('LOW_SYNTHETIC_RISK', 'MODERATE_SYNTHETIC_RISK')
        ) AS large_exposure_low_risk_condition,

        (
            cs.strategy_risk_tier IN ('HIGH_SYNTHETIC_RISK', 'SEVERE_SYNTHETIC_RISK')
            AND (
                cs.requested_exposure_tier = 'BELOW_PRODUCT_MINIMUM'
                OR cs.requested_amount <= cs.product_min_approved_amount
            )
        ) AS high_risk_low_exposure_condition,

        (
            cs.dti_bucket IN ('HIGH_DTI', 'SEVERE_DTI')
            AND cs.requested_pti_bucket IN ('LOW_REQUESTED_PTI', 'MODERATE_REQUESTED_PTI')
        ) AS high_dti_low_requested_pti_condition

    FROM core_segments cs
),

mixed_signal_scored AS (
    SELECT
        msc.*,

        /*******************************************************************************************
        mixed_signal_condition_count.

        Counts the number of mixed-signal diagnostics active on the row.

        Multiple mixed signals can coexist. Section 5 preserves that instead of forcing a single
        explanation too early.
        *******************************************************************************************/
        (
            msc.strong_credit_high_pti_condition::INT
            + msc.weak_credit_low_pti_condition::INT
            + msc.large_exposure_low_risk_condition::INT
            + msc.high_risk_low_exposure_condition::INT
            + msc.high_dti_low_requested_pti_condition::INT
        ) AS mixed_signal_condition_count

    FROM mixed_signal_conditions msc
),

borderline_scored AS (
    SELECT
        mss.*,

        /*******************************************************************************************
        Borderline profile flag.

        A row is borderline if it is within the governed percentage buffer of at least one major
        strategy threshold.

        No hidden 5%, 10%, or other ungoverned buffer is embedded. The buffer is controlled by:
            borderline_threshold_buffer_pct

        Threshold families included:
            synthetic estimated-PD proxy thresholds,
            product PTI thresholds,
            DTI thresholds,
            requested Expected Loss thresholds.

        This is diagnostic only.
        *******************************************************************************************/
        (
            (
                mss.approve_max_estimated_pd_proxy > 0
                AND ABS(mss.estimated_pd - mss.approve_max_estimated_pd_proxy)
                    <= mss.approve_max_estimated_pd_proxy * mss.borderline_threshold_buffer_pct
            )
            OR (
                mss.counteroffer_max_estimated_pd_proxy > 0
                AND ABS(mss.estimated_pd - mss.counteroffer_max_estimated_pd_proxy)
                    <= mss.counteroffer_max_estimated_pd_proxy * mss.borderline_threshold_buffer_pct
            )
            OR (
                mss.decline_min_estimated_pd_proxy > 0
                AND ABS(mss.estimated_pd - mss.decline_min_estimated_pd_proxy)
                    <= mss.decline_min_estimated_pd_proxy * mss.borderline_threshold_buffer_pct
            )

            OR (
                mss.product_approve_max_pti > 0
                AND ABS(mss.requested_payment_to_income_ratio - mss.product_approve_max_pti)
                    <= mss.product_approve_max_pti * mss.borderline_threshold_buffer_pct
            )
            OR (
                mss.product_review_max_pti > 0
                AND ABS(mss.requested_payment_to_income_ratio - mss.product_review_max_pti)
                    <= mss.product_review_max_pti * mss.borderline_threshold_buffer_pct
            )
            OR (
                mss.product_decline_min_pti > 0
                AND ABS(mss.requested_payment_to_income_ratio - mss.product_decline_min_pti)
                    <= mss.product_decline_min_pti * mss.borderline_threshold_buffer_pct
            )

            OR (
                mss.approve_max_dti > 0
                AND ABS(mss.debt_to_income_ratio - mss.approve_max_dti)
                    <= mss.approve_max_dti * mss.borderline_threshold_buffer_pct
            )
            OR (
                mss.review_max_dti > 0
                AND ABS(mss.debt_to_income_ratio - mss.review_max_dti)
                    <= mss.review_max_dti * mss.borderline_threshold_buffer_pct
            )
            OR (
                mss.decline_min_dti > 0
                AND ABS(mss.debt_to_income_ratio - mss.decline_min_dti)
                    <= mss.decline_min_dti * mss.borderline_threshold_buffer_pct
            )

            OR (
                mss.product_approve_max_requested_el > 0
                AND ABS(mss.requested_expected_loss_amount - mss.product_approve_max_requested_el)
                    <= mss.product_approve_max_requested_el * mss.borderline_threshold_buffer_pct
            )
            OR (
                mss.product_review_max_requested_el > 0
                AND ABS(mss.requested_expected_loss_amount - mss.product_review_max_requested_el)
                    <= mss.product_review_max_requested_el * mss.borderline_threshold_buffer_pct
            )
            OR (
                mss.product_decline_min_requested_el > 0
                AND ABS(mss.requested_expected_loss_amount - mss.product_decline_min_requested_el)
                    <= mss.product_decline_min_requested_el * mss.borderline_threshold_buffer_pct
            )
        ) AS borderline_profile_flag

    FROM mixed_signal_scored mss
),

final_segments AS (
    SELECT
        bs.*,

        /*******************************************************************************************
        Product × score policy segment.

        This field supports later segment-level QA, matched comparison, strategy frontier, and
        product × score evidence capture.
        *******************************************************************************************/
        bs.product_type_policy_key || '_' || bs.score_band_policy_key
            AS product_score_policy_segment,

        /*******************************************************************************************
        Mixed-signal profile type.

        Priority convention:
            If exactly one mixed-signal condition applies, assign that type.
            If more than one applies, assign MULTIPLE_MIXED_SIGNALS.
            If none applies, assign NO_MIXED_SIGNAL_PROFILE.

        Section 5 does not silently choose one condition over another when multiple conditions apply.
        *******************************************************************************************/
        CASE
            WHEN bs.mixed_signal_condition_count > 1
                THEN 'MULTIPLE_MIXED_SIGNALS'

            WHEN bs.strong_credit_high_pti_condition IS TRUE
                THEN 'STRONG_CREDIT_HIGH_PTI'

            WHEN bs.weak_credit_low_pti_condition IS TRUE
                THEN 'WEAK_CREDIT_LOW_PTI'

            WHEN bs.large_exposure_low_risk_condition IS TRUE
                THEN 'LARGE_EXPOSURE_LOW_RISK'

            WHEN bs.high_risk_low_exposure_condition IS TRUE
                THEN 'HIGH_RISK_LOW_EXPOSURE'

            WHEN bs.high_dti_low_requested_pti_condition IS TRUE
                THEN 'HIGH_DTI_LOW_REQUESTED_PTI'

            ELSE 'NO_MIXED_SIGNAL_PROFILE'
        END AS mixed_signal_profile_type

    FROM borderline_scored bs
)

SELECT *
FROM final_segments;



/***************************************************************************************************
SECTION 5.3 — LOCAL FAIL-FAST CHECKS FOR STRATEGY SEGMENTATION
****************************************************************************************************

PURPOSE:
    Validate that the Section 5 segmentation layer preserved row-level structure and produced
    complete diagnostic segments.

BUSINESS PURPOSE:
    Confirm that every selected synthetic application can be described consistently before Section 6
    creates rule-trigger flags.

LOCAL GATEKEEPER BOUNDARY:
    These are Section 5 staging gatekeepers only.

    They are not:
        final decision validation,
        reason-code validation,
        approved-exposure validation,
        archive validation,
        matched strategy comparison,
        full Module 2 QA,
        or Validation Summary evidence by themselves.

DO $$
DECLARE
    v_stage1_count BIGINT;
    v_stage2_count BIGINT;
    v_stage2_distinct_app_count BIGINT;
    v_duplicate_application_count BIGINT;

    v_null_segment_count BIGINT;
    v_null_policy_key_count BIGINT;
    v_product_policy_mismatch_count BIGINT;
    v_missing_threshold_count BIGINT;
    v_forbidden_column_count BIGINT;
BEGIN
    /*-------------------------------------------------------------------------------------------
    Gatekeeper: row count must be unchanged from Section 4 to Section 5.
    -------------------------------------------------------------------------------------------*/
    SELECT COUNT(*)
    INTO v_stage1_count
    FROM tmp_m2_stage_1_source_applications;

    SELECT COUNT(*)
    INTO v_stage2_count
    FROM tmp_m2_stage_2_strategy_segments;

    IF v_stage2_count <> v_stage1_count THEN
        RAISE EXCEPTION
            'Module 2 Section 5 failure: row count changed from Section 4 to Section 5. Stage 1 rows: %, Stage 2 rows: %.',
            v_stage1_count,
            v_stage2_count;
    END IF;


    /*-------------------------------------------------------------------------------------------
    Gatekeeper: application_id remains unique.
    -------------------------------------------------------------------------------------------*/
    SELECT COUNT(DISTINCT application_id)
    INTO v_stage2_distinct_app_count
    FROM tmp_m2_stage_2_strategy_segments;

    IF v_stage2_distinct_app_count <> v_stage2_count THEN
        SELECT COUNT(*)
        INTO v_duplicate_application_count
        FROM (
            SELECT application_id
            FROM tmp_m2_stage_2_strategy_segments
            GROUP BY application_id
            HAVING COUNT(*) > 1
        ) d;

        RAISE EXCEPTION
            'Module 2 Section 5 failure: application_id uniqueness was not preserved. Stage 2 rows: %, distinct application_id count: %, duplicate application_id group count: %.',
            v_stage2_count,
            v_stage2_distinct_app_count,
            v_duplicate_application_count;
    END IF;


    /*-------------------------------------------------------------------------------------------
