/***************************************************************************************************
SECTION 15.0 — FRONTIER SCOPE AND ARCHIVE READINESS SNAPSHOT
****************************************************************************************************

PURPOSE:
    Provide a quick archive-level readiness snapshot before creating strategy frontier outputs.

BUSINESS PURPOSE:
    Confirm whether the archive contains enough completed strategy / scenario slices to support
    frontier analysis.

SQL PURPOSE:
    1. Count archived rows.
    2. Count distinct archived application_id values.
    3. Count archived strategy × scenario slices.
    4. Count Module 1 scenario / population slices.
    5. Count Module 2 strategy versions.
    6. Display archive timestamp range.
    7. Assign a frontier_scope_status.

FRONTIER READINESS INTERPRETATION:
    FRONTIER_NOT_READY_ARCHIVE_EMPTY:
        No archived rows exist.

    FRONTIER_INVENTORY_ONLY_SINGLE_ARCHIVED_SLICE:
        Only one archived strategy / scenario slice exists.
        Section 15 can summarize inventory, but it cannot yet show strategy tradeoffs.

    FRONTIER_READY_FOR_MULTI_STRATEGY_REVIEW:
        At least two Module 2 strategy versions exist in the archive.
        Section 15 can begin to show multi-strategy frontier tradeoffs.

    FRONTIER_AVAILABLE_FOR_ARCHIVE_REVIEW:
        Archive contains rows and can be summarized, though richer frontier interpretation may depend
        on the mix of scenarios and strategies available.

BOUNDARY:
    This is a read-only diagnostic.

    It does not require a baseline strategy to exist.
    It does not require campaign registry mapping.
    It does not modify archive rows.
    It does not validate the latest-run output.
    It does not perform matched comparison.

***************************************************************************************************/

SELECT
    'SECTION_15_FRONTIER_SCOPE' AS diagnostic_name,

    COUNT(*) AS archived_rows,
    COUNT(DISTINCT application_id) AS distinct_archived_application_ids,

    COUNT(DISTINCT
        strategy_set_name
        || '|' || strategy_name
        || '|' || strategy_version
        || '|' || module1_scenario_set_name
        || '|' || module1_scenario_name
        || '|' || population_id
    ) AS archived_strategy_scenario_slice_count,

    COUNT(DISTINCT
        module1_scenario_set_name
        || '|' || module1_scenario_name
        || '|' || population_id
    ) AS module1_scenario_population_slice_count,

    COUNT(DISTINCT
        strategy_set_name
        || '|' || strategy_name
        || '|' || strategy_version
    ) AS module2_strategy_version_count,

    MIN(archive_inserted_ts) AS min_archive_inserted_ts,
    MAX(archive_inserted_ts) AS max_archive_inserted_ts,

    CASE
        WHEN COUNT(*) = 0
            THEN 'FRONTIER_NOT_READY_ARCHIVE_EMPTY'

        WHEN COUNT(DISTINCT
                strategy_set_name
                || '|' || strategy_name
                || '|' || strategy_version
                || '|' || module1_scenario_set_name
                || '|' || module1_scenario_name
                || '|' || population_id
             ) = 1
            THEN 'FRONTIER_INVENTORY_ONLY_SINGLE_ARCHIVED_SLICE'

        WHEN COUNT(DISTINCT
                strategy_set_name
                || '|' || strategy_name
                || '|' || strategy_version
             ) >= 2
            THEN 'FRONTIER_READY_FOR_MULTI_STRATEGY_REVIEW'

        ELSE 'FRONTIER_AVAILABLE_FOR_ARCHIVE_REVIEW'
    END AS frontier_scope_status

FROM credit_decisioning_sim.strategy_decisions_archive;

DO $$
BEGIN
    IF TO_REGCLASS('credit_decisioning_sim.strategy_run_campaign_registry') IS NULL THEN

        /*******************************************************************************************
        Registry table is unavailable.

        Create an empty registry map so the rest of Section 15 can run with LEFT JOIN semantics.
        *******************************************************************************************/
        CREATE TEMP TABLE tmp_m2_strategy_frontier_campaign_registry_map (
            module1_run_id                       TEXT,
            module2_run_id                       TEXT,
            run_sequence_number                  INTEGER,

            showcase_id                          TEXT,
            showcase_name                        TEXT,
            comparison_group_id                  TEXT,
            validation_evidence_group_id         TEXT,

            module1_scenario_set_name            TEXT,
            module1_scenario_name                TEXT,
            population_id                        TEXT,

            strategy_set_name                    TEXT,
            strategy_name                        TEXT,
            strategy_version                     TEXT,

            readme_storyline_label               TEXT,
            linkedin_post_sequence               INTEGER,
            validation_summary_section_hint       TEXT,

            registry_active_flag                 BOOLEAN,
            registry_match_count                 BIGINT,
            frontier_registry_match_status        TEXT
        ) ON COMMIT PRESERVE ROWS;

    ELSE

        /*******************************************************************************************
        Registry table is available.

        Build a one-row-per-technical-key active registry map.

        ROW_NUMBER protects Section 15 from accidental duplicate active registry rows.
        registry_match_count surfaces duplicate mapping risk for review.
        *******************************************************************************************/
        CREATE TEMP TABLE tmp_m2_strategy_frontier_campaign_registry_map
        ON COMMIT PRESERVE ROWS
        AS
        WITH registry_ranked AS (
            SELECT
                r.module1_run_id,
                r.module2_run_id,
                r.run_sequence_number,

                r.showcase_id,
                r.showcase_name,
                r.comparison_group_id,
                r.validation_evidence_group_id,

                r.module1_scenario_set_name,
                r.module1_scenario_name,
                r.population_id,

                r.strategy_set_name,
                r.strategy_name,
                r.strategy_version,

                r.readme_storyline_label,
                r.linkedin_post_sequence,
                r.validation_summary_section_hint,

                r.registry_active_flag,

                COUNT(*) OVER (
                    PARTITION BY
                        r.module1_scenario_set_name,
                        r.module1_scenario_name,
                        r.population_id,
                        r.strategy_set_name,
                        r.strategy_name,
                        r.strategy_version
                ) AS registry_match_count,

                ROW_NUMBER() OVER (
                    PARTITION BY
                        r.module1_scenario_set_name,
                        r.module1_scenario_name,
                        r.population_id,
                        r.strategy_set_name,
                        r.strategy_name,
                        r.strategy_version
                    ORDER BY
                        r.run_sequence_number NULLS LAST,
                        r.module2_run_id
                ) AS registry_rank

            FROM credit_decisioning_sim.strategy_run_campaign_registry r

            WHERE r.registry_active_flag IS TRUE
        )

        SELECT
            module1_run_id,
            module2_run_id,
            run_sequence_number,

            showcase_id,
            showcase_name,
            comparison_group_id,
            validation_evidence_group_id,

            module1_scenario_set_name,
            module1_scenario_name,
            population_id,

            strategy_set_name,
            strategy_name,
            strategy_version,

            readme_storyline_label,
            linkedin_post_sequence,
            validation_summary_section_hint,

            registry_active_flag,
            registry_match_count,

            CASE
                WHEN registry_match_count = 1
                    THEN 'FRONTIER_REGISTRY_MATCHED'
                ELSE 'FRONTIER_REGISTRY_DUPLICATE_MATCH_REVIEW'
            END AS frontier_registry_match_status

        FROM registry_ranked

        WHERE registry_rank = 1;
    END IF;
END $$;

AS

    strategy_name,
    strategy_version,

    module1_scenario_set_name,
    module1_scenario_name,
    population_id,

    COUNT(*) AS archived_row_count,
    COUNT(DISTINCT application_id) AS distinct_application_id_count,

    MAX(latest_output_created_ts) AS max_latest_output_created_ts,

    MAX(archive_inserted_ts) AS max_archive_inserted_ts,

    COUNT(*) FILTER (WHERE decision_outcome = 'COUNTEROFFER') AS counteroffer_count,
    COUNT(*) FILTER (WHERE decision_outcome = 'MANUAL_REVIEW') AS manual_review_count,
    COUNT(*) FILTER (WHERE decision_outcome = 'DECLINE') AS decline_count,

    COUNT(*) FILTER (WHERE simulated_offer_exposure_flag IS TRUE)
        AS simulated_offer_exposure_count

FROM credit_decisioning_sim.strategy_decisions_archive

GROUP BY
    strategy_set_name,
    strategy_name,
    strategy_version,
    module1_scenario_set_name,
    module1_scenario_name,
    population_id;

/***************************************************************************************************

****************************************************************************************************

PURPOSE:
    Produce one summary row per archived Module 1 scenario × Module 2 strategy slice.

BUSINESS PURPOSE:
    Create the core frontier summary table that converts archived applicant-level strategy outputs
    into portfolio-level strategy tradeoff metrics.

    This section answers:

        "For each archived strategy / scenario slice, what are the core access, exposure, risk,
         affordability, Expected Loss, and reason-code characteristics?"

SQL PURPOSE:
    1. Materialize tmp_m2_strategy_frontier_summary.
    2. Calculate final decision counts and rates.
    3. Calculate simulated positive offer-exposure counts and rates.
    4. Calculate approval and counteroffer shares among offer rows.
    5. Calculate requested amount and approved amount totals / averages.
    6. Calculate counteroffer exposure-reduction averages.
    7. Calculate requested PTI and approved PTI averages.
    8. Calculate synthetic estimated-risk proxy averages across all rows, offer rows, declined rows,
       and manual-review rows.
    9. Calculate LGD averages.
    10. Calculate requested Expected Loss and approved Expected Loss metrics.
    11. Calculate requested and approved Expected Loss rates.
    12. Identify top primary reason code.
    13. Identify top non-approval reason code.
    14. Identify top policy-stop reason code.

BUSINESS INTERPRETATION:
    This is the core strategy frontier table.

    It summarizes:
        decision distribution,
        simulated offer exposure,
        approved amount,
        approved affordability,
        synthetic estimated-risk profile,
        requested Expected Loss,
        approved Expected Loss,
        approved Expected Loss rate,
        and primary reason-code concentration.

METRIC CONVENTIONS:
    approval_rate:
        approval_count / applications

    counteroffer_rate:
        counteroffer_count / applications

    manual_review_rate:
        manual_review_count / applications

    decline_rate:
        decline_count / applications

    simulated_offer_exposure_rate:
        simulated_offer_exposure_count / applications

    approval_share_of_offers:
        approval_count / simulated_offer_exposure_count

    counteroffer_share_of_offers:
        counteroffer_count / simulated_offer_exposure_count

    requested_expected_loss_rate:
        total_requested_expected_loss_amount / total_requested_amount

    approved_expected_loss_rate:
        total_approved_expected_loss_amount / total_approved_amount

    All-application approved exposure metrics:
        Use COALESCE(approved_amount, 0)
        Use COALESCE(approved_expected_loss_amount, 0)

    Offer-row metrics:
        Use FILTER (WHERE simulated_offer_exposure_flag IS TRUE)

WHY NON-APPROVAL REASON FIELDS ARE INCLUDED:
    top_primary_reason_code is often APPROVED_AS_REQUESTED.

    That is technically correct but not always the most useful executive explanation of strategy
    movement.

    top_non_approval_primary_reason_code and top_policy_stop_primary_reason_code help explain what
    constrains access, drives reduced exposure, or concentrates final no-offer outcomes.

BOUNDARY:

WITH slice_summary AS (

        strategy_set_name,
        strategy_name,
        strategy_version,

        module1_scenario_set_name,
        module1_scenario_name,
        population_id,

        COUNT(*) FILTER (WHERE decision_outcome = 'MANUAL_REVIEW') AS manual_review_count,
        COUNT(*) FILTER (WHERE decision_outcome = 'DECLINE') AS decline_count,

        COUNT(*) FILTER (WHERE simulated_offer_exposure_flag IS TRUE)
            AS simulated_offer_exposure_count,

        COUNT(*) FILTER (WHERE decision_outcome = 'APPROVE')::NUMERIC
            / NULLIF(COUNT(*), 0) AS approval_rate,

        COUNT(*) FILTER (WHERE decision_outcome = 'COUNTEROFFER')::NUMERIC
            / NULLIF(COUNT(*), 0) AS counteroffer_rate,

        COUNT(*) FILTER (WHERE decision_outcome = 'MANUAL_REVIEW')::NUMERIC
            / NULLIF(COUNT(*), 0) AS manual_review_rate,

        COUNT(*) FILTER (WHERE decision_outcome = 'DECLINE')::NUMERIC
            / NULLIF(COUNT(*), 0) AS decline_rate,

        COUNT(*) FILTER (WHERE simulated_offer_exposure_flag IS TRUE)::NUMERIC
            / NULLIF(COUNT(*), 0) AS simulated_offer_exposure_rate,

        COUNT(*) FILTER (WHERE decision_outcome = 'APPROVE')::NUMERIC
            / NULLIF(COUNT(*) FILTER (WHERE simulated_offer_exposure_flag IS TRUE), 0)
            AS approval_share_of_offers,

        COUNT(*) FILTER (WHERE decision_outcome = 'COUNTEROFFER')::NUMERIC
            / NULLIF(COUNT(*) FILTER (WHERE simulated_offer_exposure_flag IS TRUE), 0)

        SUM(requested_amount) AS total_requested_amount,
        SUM(COALESCE(approved_amount, 0)) AS total_approved_amount,

            AS avg_requested_payment_to_income_ratio,

        AVG(approved_payment_to_income_ratio) FILTER (WHERE simulated_offer_exposure_flag IS TRUE)
            AS avg_approved_payment_to_income_ratio_offer_rows,

        AVG(estimated_pd) AS avg_synthetic_estimated_pd_proxy_all_apps,

        AVG(estimated_pd) FILTER (WHERE simulated_offer_exposure_flag IS TRUE)
            AS avg_synthetic_estimated_pd_proxy_offer_rows,

        AVG(estimated_pd) FILTER (WHERE decision_outcome = 'DECLINE')
            AS avg_synthetic_estimated_pd_proxy_declined_rows,

        AVG(estimated_pd) FILTER (WHERE decision_outcome = 'MANUAL_REVIEW')
            AS avg_synthetic_estimated_pd_proxy_manual_review_rows,

        AVG(estimated_lgd) AS avg_estimated_lgd_all_apps,

        AVG(estimated_lgd) FILTER (WHERE simulated_offer_exposure_flag IS TRUE)

        SUM(COALESCE(approved_expected_loss_amount, 0))

        AVG(COALESCE(approved_expected_loss_amount, 0))

        AVG(approved_expected_loss_amount) FILTER (WHERE simulated_offer_exposure_flag IS TRUE)
            AS avg_approved_expected_loss_offer_rows,

            / NULLIF(SUM(requested_amount), 0)
            AS requested_expected_loss_rate,

        SUM(COALESCE(approved_expected_loss_amount, 0))
            / NULLIF(SUM(COALESCE(approved_amount, 0)), 0)
            AS approved_expected_loss_rate

    GROUP BY
        strategy_set_name,
        strategy_name,
        strategy_version,
        module1_scenario_set_name,
        module1_scenario_name,

                        strategy_version,

        strategy_version,
        module1_scenario_set_name,
        module1_scenario_name,
        population_id,
        primary_reason_family,
        primary_reason_code

non_approval_reason_counts AS (

        strategy_name,
        strategy_version,

        module1_scenario_set_name,
        module1_scenario_name,
        population_id,

        primary_reason_family,
        primary_reason_code,

                strategy_set_name,
                strategy_name,
                strategy_version,
                module1_scenario_set_name,
                module1_scenario_name,

        strategy_name,
        strategy_version,
        module1_scenario_set_name,
        module1_scenario_name,
        population_id,
        primary_reason_family,

        module1_scenario_name,

                strategy_version,

                module1_scenario_name,

        strategy_name,
        strategy_version,
        module1_scenario_set_name,
        module1_scenario_name,

        primary_reason_family,
        primary_reason_code

    nr.primary_reason_family AS top_non_approval_primary_reason_family,

FROM slice_summary s

LEFT JOIN reason_counts r

   AND r.module1_scenario_set_name = s.module1_scenario_set_name
   AND r.module1_scenario_name = s.module1_scenario_name

   AND nr.strategy_name = s.strategy_name
   AND nr.strategy_version = s.strategy_version
   AND nr.module1_scenario_set_name = s.module1_scenario_set_name
   AND nr.module1_scenario_name = s.module1_scenario_name
   AND nr.population_id = s.population_id
   AND nr.non_approval_reason_rank = 1

LEFT JOIN policy_stop_reason_counts ps
    ON ps.strategy_set_name = s.strategy_set_name
   AND ps.strategy_name = s.strategy_name
   AND ps.strategy_version = s.strategy_version
   AND ps.module1_scenario_set_name = s.module1_scenario_set_name
   AND ps.module1_scenario_name = s.module1_scenario_name
   AND ps.population_id = s.population_id
   AND ps.policy_stop_reason_rank = 1;

/***************************************************************************************************
SECTION 15.3 — BASELINE-RELATIVE FRONTIER DELTAS
****************************************************************************************************

PURPOSE:
    Calculate baseline-relative deltas for each archived strategy slice where a baseline strategy
    exists for the same Module 1 scenario / population / strategy set.

BUSINESS PURPOSE:
    Make frontier interpretation sharper by anchoring each non-baseline strategy point to a
    consistent baseline reference.

    This section answers:

        "Relative to BASELINE_STRATEGY on the same Module 1 scenario and population, what changed in
         access, exposure, approved Expected Loss, affordability, offered-population synthetic risk,
         and reason-code distribution?"

BASELINE DEFINITION:
    The baseline reference is identified by:

        strategy_name = 'BASELINE_STRATEGY'

    within the same:
        strategy_set_name
        module1_scenario_set_name
        module1_scenario_name
        population_id

WHY THIS MATTERS:
    Frontier analysis is more interpretable when strategy points are compared against a consistent
    baseline reference.

    It helps distinguish:
        absolute strategy posture,
        versus baseline-relative movement.

BASELINE UNAVAILABLE BOUNDARY:
    If no baseline strategy exists for a scenario / strategy set, baseline-relative fields are NULL
    and baseline_available_flag is FALSE.

    This is diagnostic behavior, not a failure.

REASON-CODE DELTA DRIVER:
    top_reason_code_delta_driver_* fields identify the simulated reason code with the largest
    population-share movement versus baseline.

    This helps explain not only what changed numerically, but why the strategy frontier point moved.

READ-ONLY BOUNDARY:
    This section reads from archive-derived temporary tables and archive reason-code counts only.

    It does not mutate archive rows.
    It does not recalculate applicant outcomes.
    It does not reassign reason codes.

***************************************************************************************************/

DROP TABLE IF EXISTS tmp_m2_strategy_frontier_baseline_deltas;

reason_population_shares AS (

        strategy_version,

                        strategy_name,
                        strategy_version,
                        module1_scenario_set_name,
                        module1_scenario_name,
                        population_id

                0

        strategy_set_name,

                    COALESCE(rs.reason_population_share, 0)

        ) AS reason_code_delta_rank

        ON br.strategy_set_name = s.strategy_set_name

       AND br.module1_scenario_name = s.module1_scenario_name
       AND br.population_id = s.population_id
       AND br.primary_reason_family = u.primary_reason_family
       AND br.primary_reason_code = u.primary_reason_code

)

    b.strategy_name AS baseline_strategy_name,
    b.strategy_version AS baseline_strategy_version,

    s.avg_synthetic_estimated_pd_proxy_offer_rows
      - b.avg_synthetic_estimated_pd_proxy_offer_rows
        AS delta_avg_synthetic_estimated_pd_proxy_offer_rows,

    s.top_policy_stop_primary_reason_family,

    td.top_reason_code_delta_driver_family,

/***************************************************************************************************

PURPOSE:

BUSINESS PURPOSE:

    executive discussion, README interpretation, and LinkedIn storytelling.

    This section answers:

        "What kind of tradeoff does this archived strategy point appear to represent?"

SQL PURPOSE:
    1. Materialize tmp_m2_strategy_frontier_classification.
    2. Preserve efficiency metrics and baseline-relative deltas.
    3. Assign frontier_position_type.
    4. Assign frontier_interpretation_note.
    5. Display classification output with relevant frontier metrics.

FRONTIER POSITION TYPES:
    BASELINE_REFERENCE_POINT:
        Baseline strategy under the same scenario / population / strategy set.

    NO_BASELINE_REFERENCE_AVAILABLE:
        Strategy slice exists but baseline-relative deltas are unavailable.

    RISK_DISCIPLINE_FRONTIER_POINT:
        Strategy reduces simulated offer exposure and approved Expected Loss while improving the
        offered-population synthetic estimated-risk profile.

    GROWTH_ORIENTED_FRONTIER_POINT:
        Strategy expands simulated offer exposure and approved amount with measurable approved
        Expected Loss tradeoff.

    EXPOSURE_EFFICIENT_FRONTIER_POINT:
        Strategy improves approved Expected Loss while maintaining or expanding total approved amount.

    COUNTEROFFER_MANAGEMENT_FRONTIER_POINT:
        Strategy shifts outcomes toward reduced-exposure treatment rather than clean approval.

    REVIEW_BURDEN_REDUCTION_FRONTIER_POINT:
        Strategy reduces unresolved manual-review burden by routing more cases to final no-offer
        outcomes.

    BALANCED_OR_MIXED_FRONTIER_POINT:
        Strategy shows mixed tradeoffs requiring segment-level and reason-code review.

CLASSIFICATION BOUNDARY:
    These labels are diagnostic summaries.

    They do not declare a strategy "best."
    They do not recommend production use.
    They do not replace Section 13 matched comparison.
    They do not replace Section 14 validation.
    They do not represent model validation approval.

DIAGNOSTIC THRESHOLD NOTE:
    Small threshold values are used only to avoid labeling immaterial changes as strategic movement.

    These thresholds are not:
        credit policy thresholds,
        underwriting cutoffs,
        production acceptance thresholds,
        calibrated empirical performance thresholds,
        or regulatory standards.

***************************************************************************************************/

DROP TABLE IF EXISTS tmp_m2_strategy_frontier_classification;

CREATE TEMP TABLE tmp_m2_strategy_frontier_classification
ON COMMIT PRESERVE ROWS
AS
SELECT
    e.*,

    CASE
        WHEN e.strategy_name = 'BASELINE_STRATEGY'
            THEN 'BASELINE_REFERENCE_POINT'

        WHEN e.baseline_available_flag IS DISTINCT FROM TRUE
            THEN 'NO_BASELINE_REFERENCE_AVAILABLE'

        WHEN e.delta_simulated_offer_exposure_rate <= -0.010
         AND e.delta_total_approved_expected_loss_amount < 0
         AND e.delta_avg_synthetic_estimated_pd_proxy_offer_rows < 0
            THEN 'RISK_DISCIPLINE_FRONTIER_POINT'

        WHEN e.delta_simulated_offer_exposure_rate >= 0.010
         AND e.delta_total_approved_amount > 0
         AND e.delta_total_approved_expected_loss_amount >= 0
            THEN 'GROWTH_ORIENTED_FRONTIER_POINT'

        WHEN e.delta_total_approved_expected_loss_amount < 0
         AND e.delta_total_approved_amount >= 0
            THEN 'EXPOSURE_EFFICIENT_FRONTIER_POINT'

        WHEN e.delta_counteroffer_rate >= 0.010
         AND e.delta_approval_rate <= 0
            THEN 'COUNTEROFFER_MANAGEMENT_FRONTIER_POINT'

        WHEN e.delta_manual_review_rate <= -0.010
         AND e.delta_decline_rate > 0
            THEN 'REVIEW_BURDEN_REDUCTION_FRONTIER_POINT'

        ELSE 'BALANCED_OR_MIXED_FRONTIER_POINT'
    END AS frontier_position_type,

    CASE
        WHEN e.strategy_name = 'BASELINE_STRATEGY'
            THEN 'Reference point for same Module 1 scenario / population / strategy set.'

        WHEN e.baseline_available_flag IS DISTINCT FROM TRUE
            THEN 'No baseline strategy slice exists for this Module 1 scenario / population / strategy set.'

        WHEN e.delta_simulated_offer_exposure_rate <= -0.010
         AND e.delta_total_approved_expected_loss_amount < 0
         AND e.delta_avg_synthetic_estimated_pd_proxy_offer_rows < 0
            THEN 'Strategy reduces simulated offer exposure and approved Expected Loss while improving offered-population synthetic estimated-risk profile.'

        WHEN e.delta_simulated_offer_exposure_rate >= 0.010
         AND e.delta_total_approved_amount > 0
         AND e.delta_total_approved_expected_loss_amount >= 0
            THEN 'Strategy expands simulated offer exposure and approved amount with measurable approved Expected Loss tradeoff.'

        WHEN e.delta_total_approved_expected_loss_amount < 0
         AND e.delta_total_approved_amount >= 0
            THEN 'Strategy improves approved Expected Loss while maintaining or expanding total approved amount.'

        WHEN e.delta_counteroffer_rate >= 0.010
         AND e.delta_approval_rate <= 0
            THEN 'Strategy shifts outcomes toward reduced-exposure treatment rather than clean approval.'

        WHEN e.delta_manual_review_rate <= -0.010
         AND e.delta_decline_rate > 0
            THEN 'Strategy reduces unresolved manual-review burden by routing more cases to final no-offer outcomes.'

        ELSE 'Strategy shows mixed tradeoffs requiring segment-level and reason-code review.'
    END AS frontier_interpretation_note

FROM tmp_m2_strategy_frontier_efficiency e;

ON COMMIT PRESERVE ROWS
AS

        'PRODUCT_X_SCORE'::TEXT AS segment_level,
        product_type_policy_key || ' / ' || score_band_policy_key AS segment_key,
        product_type_policy_key,
        score_band_policy_key,

        strategy_set_name,
        strategy_name,
        strategy_version,
        module1_scenario_set_name,
        module1_scenario_name,
        population_id,

        COUNT(*) FILTER (WHERE decision_outcome = 'DECLINE')::NUMERIC
            / NULLIF(COUNT(*), 0) AS decline_rate,

        SUM(COALESCE(approved_expected_loss_amount, 0))
            / NULLIF(SUM(COALESCE(approved_amount, 0)), 0)
            AS approved_expected_loss_rate,

        AVG(estimated_pd) FILTER (WHERE simulated_offer_exposure_flag IS TRUE)
            AS avg_synthetic_estimated_pd_proxy_offer_rows,

        AVG(approved_payment_to_income_ratio) FILTER (WHERE simulated_offer_exposure_flag IS TRUE)
            AS avg_approved_payment_to_income_ratio_offer_rows

    GROUP BY

        segment_key,
        product_type_policy_key,

                strategy_name,
                strategy_version,
                module1_scenario_set_name,
                module1_scenario_name,

                primary_reason_code

    GROUP BY
        segment_level,
        segment_key,
        product_type_policy_key,
        score_band_policy_key,
        strategy_set_name,
        strategy_name,
        strategy_version,
        module1_scenario_set_name,
        module1_scenario_name,
        population_id,
        primary_reason_family,
        primary_reason_code
)

SELECT
    s.*,

    r.primary_reason_family AS top_segment_reason_family,
    r.primary_reason_code AS top_segment_reason_code,
    r.reason_row_count AS top_segment_reason_row_count

FROM segment_summary s

LEFT JOIN segment_reason_counts r
    ON r.segment_level = s.segment_level
   AND r.segment_key = s.segment_key

0.5 CORE DESIGN PRINCIPLES
====================================================================================================

Module 2 follows these design principles:

1. Strategy-parameterized over hard-coded
    Strategy behavior should be changed through governed parameters before changing downstream CASE
    logic. This supports controlled strategy tuning, repeatability, and auditability.

2. Staged over monolithic
    Module 2 is built in layers:
        source staging,
        segmentation,
        rule flags,
        preliminary routing,
        exposure treatment,
        final decision resolution,
        reason-code assignment,
        output materialization,
        archive persistence,
        comparison,
        QA,
        frontier summary,
        and evidence capture.

    This makes the engine easier to validate, debug, and explain.

3. Explainable over opaque
    Every major outcome should be traceable through:
        segmentation fields,
        rule-trigger flags,
        preliminary routing,
        exposure-treatment diagnostics,
        final decision fields,
        and simulated strategy explanation codes.

4. Simulated outcomes over operational decisions
    APPROVE, COUNTEROFFER, MANUAL_REVIEW, and DECLINE are simulated strategy outcomes for synthetic
    applicants. They are not real applicant treatments.

5. Reason-code transparency over black-box routing
    Simulated reason codes are used for strategy explanation, QA, portfolio diagnostics, and
    decision-path traceability.

6. Matched comparison over population drift
    Strategy comparison should hold Module 1 scenario and population constant when isolating
    downstream Module 2 strategy effects.

7. Governed archive over ad hoc outputs
    The latest-run table is replaceable. The archive table preserves completed strategy outputs and
    enables matched comparison.

8. Diagnostics before documentation
    Validation Summary and README claims should be based on captured SQL evidence, not narrative
    assertion.

9. Evidence capture over scattered manual notes
    Section 16 persists executive story, validation evidence, parameter snapshots, and product × score
    segment evidence so future documentation can reference stable run IDs and evidence tables.

10. Modular expansion over scope creep
    Growth, earnings, funding cost, risk-adjusted margin, pricing, and profitability belong to a
    future Module 3 economics layer.

SQL LEARNING POINT:
    The staged-table pattern is intentionally used because it makes intermediate logic inspectable.

    A reviewer can inspect:
        tmp_m2_stage_2_strategy_segments
        before rule flags exist,

        tmp_m2_stage_3_rule_flags
        before routing exists,

        tmp_m2_stage_5_exposure_treatment
        before final decision resolution exists.

    That staged design is a SQL-native way to support auditability and debugging.

0.7 PARAMETER CHANGE GUIDANCE

Users should tune Module 2 by changing governed parameters first.

Preferred strategy-change workflow:

    1. Define the business question.
    2. Decide whether the question is about risk appetite, affordability, DTI capacity, exposure,

    5. Run the module.
    6. Review Section 14 QA and Section 15 frontier outputs.
    7. Capture Section 16 evidence.
    8. Document the observed behavior.

governed parameters.

Parameter changes should be interpreted as simulated strategy tuning, not empirical model calibration.

CREDIT RISK LEARNING POINT:
    A risk-tightening strategy is not automatically "better."

    It may reduce approved Expected Loss while also reducing access, lowering approved exposure,
    increasing decline rate, or shifting burden into manual review.

    A growth strategy is not automatically "worse."

    It may expand access and approved amount while increasing approved Expected Loss.

    The analytical task is to understand the tradeoff, not to force a single universal answer.

0.8 TESTING AND VALIDATION GUIDANCE
====================================================================================================

A successful SQL run is not the same as a validated strategy run.

A completed Module 2 run should be reviewed across multiple evidence layers:

    1. Structural integrity
        row count,
        application_id uniqueness,
        strategy lineage,
        Module 1 scenario lineage.

    2. Final outcome integrity
        one final decision_outcome per row,
        final flags reconcile,
        simulated_offer_exposure_flag aligns to APPROVE and COUNTEROFFER.

    3. Amount and economics conventions
        APPROVE preserves requested exposure,
        COUNTEROFFER reduces exposure,
        MANUAL_REVIEW remains unresolved,
        DECLINE uses zero-exposure convention.

    4. Risk and affordability behavior
        synthetic estimated-risk tiers,
        requested PTI buckets,
        DTI buckets,
        requested versus approved PTI.

    5. Counteroffer behavior
        feasibility pass / fail,
        exposure reduction,
        approved PTI target,
        approved Expected Loss cap.

    6. Reason-code coverage
        every row explainable,
        reason family aligns to final outcome,
        reason-code concentration reviewed.

    7. Archive persistence
        archived slice row count equals latest-run row count,
        archive grain is unique,
        persisted values match latest-run values.

    8. Matched comparison
        baseline and challenger share the same Module 1 scenario and population,
        application_id overlap is complete,
        source fields match,
        strategy deltas are interpretable.

    9. Frontier and evidence capture
        Section 15 summarizes strategy tradeoffs,
        Section 16 stores the executive and validation evidence needed for documentation.

SQL LEARNING POINT:
    Validation queries usually do one of three things:

        1. Count violations.
            Example:
                COUNT(*) FILTER (WHERE final flag count <> 1)

        2. Compare expected versus observed populations.
            Example:
                latest-run row count versus archived slice row count

        3. Summarize directional behavior.
            Example:
                approval rate by risk tier or score band

    These patterns are repeated throughout Sections 12 through 16.

0.10 FINAL DECISION TAXONOMY
====================================================================================================

Module 2 uses exactly four final decision_outcome values:

    APPROVE
    COUNTEROFFER
    MANUAL_REVIEW
    DECLINE

APPROVE:
    Clean simulated positive offer outcome as requested.

COUNTEROFFER:
    Simulated positive offer outcome with reduced approved exposure.
    COUNTEROFFER is distinct from APPROVE.

MANUAL_REVIEW:
    Unresolved simulated strategy outcome.
    No approved exposure or approved Expected Loss is assigned.

DECLINE:
    Simulated no-offer outcome using the zero-exposure convention.

CREDIT RISK LEARNING POINT:
    Separating APPROVE from COUNTEROFFER matters.

    A counteroffer is still simulated positive offer exposure, but it is not the same as approving the
    requested structure.

    This distinction allows strategy reviewers to evaluate whether a strategy is preserving access by
    reducing exposure rather than simply approving or declining.

====================================================================================================
0.11 COUNTEROFFER DESIGN BOUNDARY
====================================================================================================

COUNTEROFFER is a distinct final decision_outcome.

More detailed counteroffer interpretation is captured through:
    decision_path,
    counteroffer feasibility diagnostics,
    exposure-treatment fields,
    simulated reason codes,
    and frontier / evidence summaries.

A preliminary counteroffer route does not guarantee a final feasible counteroffer.

Final COUNTEROFFER is assigned only after approved exposure, approved PTI, and approved Expected Loss
feasibility have been evaluated.

SQL LEARNING POINT:

        product cap amount,
        PTI target amount,
        approved Expected Loss cap amount,
        minimum viable amount,
        conservative rounding,
        feasibility testing,
        final decision resolution.

    These are not cleanly represented by a single CASE expression without losing auditability.

0.18 SQL PATTERNS USED THROUGHOUT MODULE 2
====================================================================================================

This module repeatedly uses a small number of SQL patterns.

Understanding these patterns will make the rest of the file easier to read.

1. CREATE TEMP TABLE ... AS SELECT
    Used to materialize a staging layer.

    Why:
        It makes intermediate transformation logic inspectable.

2. WITH common_table_expressions AS (...)
    Used to break complex logic into named steps.

    Why:
        It allows readers to follow the transformation path instead of reading one giant nested query.

3. SELECT DISTINCT
    Used when converting applicant-grain output into run-grain helper tables.

    Why:
        Applicant-level rows repeat run metadata. DISTINCT collapses that repeated metadata into a
        single run key.

4. COUNT(*) FILTER (WHERE condition)
    Used for compact validation and outcome-rate logic.

    Why:
        It lets one query calculate many conditional counts without separate subqueries.

5. NULLIF(denominator, 0)
    Used to prevent divide-by-zero errors.

    Why:
        Validation and segmentation queries should remain stable even when a population segment has
        zero rows.

6. COALESCE(value, fallback)
    Used when preserving portfolio-impact metrics or fallback metadata.

    Why:
        It makes NULL handling explicit.

7. IS DISTINCT FROM
    Used for safe equality checks when NULLs may exist.

    Why:
        Unlike ordinary equality, IS DISTINCT FROM treats NULL versus non-NULL as a comparable
        difference.

8. ROW_NUMBER() OVER (...)
    Used for deterministic ranking.

    Why:
        It supports top reason-code selection, top segment selection, and duplicate-safe registry
        mapping.

approval_rate:
    APPROVE rows / all applications in the relevant population.

counteroffer_rate:
    COUNTEROFFER rows / all applications in the relevant population.

manual_review_rate:
    MANUAL_REVIEW rows / all applications in the relevant population.

decline_rate:
    DECLINE rows / all applications in the relevant population.

simulated_offer_exposure_rate:
    APPROVE + COUNTEROFFER rows / all applications in the relevant population.

approval_share_of_offers:
    APPROVE rows / simulated positive offer-exposure rows.

counteroffer_share_of_offers:
    COUNTEROFFER rows / simulated positive offer-exposure rows.

approved_expected_loss_rate:
    total approved Expected Loss / total approved amount.

CREDIT RISK LEARNING POINT:
    A strategy can have a high approval rate but still be weak if approved Expected Loss is too high.

    A strategy can have lower approval but stronger risk discipline if approved Expected Loss falls
    meaningfully and risk ordering improves.

    A strategy can preserve access through counteroffers while reducing approved exposure.

    That is why Module 2 evaluates multiple metrics rather than a single approval-rate statistic.

/***************************************************************************************************
SECTION 1 — SCHEMA SETUP / CLEAN RERUN RESET
****************************************************************************************************

BUSINESS PURPOSE:
    Establish the dedicated simulation schema and reset transient Module 2 execution objects so a
    full Module 2 run starts from a clean, interpretable state.

    Section 1 answers:

        "What execution artifacts should be cleared before a new full Module 2 strategy run begins,
         and what governed history should be preserved?"

SQL PURPOSE:
    1. Create or reuse the dedicated simulation schema.
    2. Set the search path for convenient object resolution.
    3. Drop temporary Module 2 parameter, staging, comparison, validation, frontier, and evidence
       helper objects from prior executions.
    4. Drop the replaceable latest-run strategy output table for clean rerun behavior.
    5. Preserve the governed archive, campaign registry, and evidence history tables.

INPUTS:
    None required.

OUTPUTS:
    credit_decisioning_sim schema exists.
    Prior temporary Module 2 execution objects are removed.
    credit_decisioning_sim.strategy_decisions is removed so the current run can rebuild it.
    credit_decisioning_sim.strategy_decisions_archive is preserved.
    Persistent evidence and campaign registry tables are preserved.

WHY THIS SECTION EXISTS:
    Module 2 is intentionally staged.

    A prior failed run, partial run, or exploratory run can leave temporary objects in the active
    session. Those temporary objects should not silently influence the next full strategy execution.

    Section 1 therefore resets transient execution artifacts before the parameter framework,
    source-selection layer, decision stages, QA layers, frontier summary, and evidence capture are
    rebuilt.

WHY THE LATEST-RUN TABLE MAY BE DROPPED:
    credit_decisioning_sim.strategy_decisions represents the current completed Module 2 strategy run
    only.

    It is not the history table.
    It is not the comparison archive.
    It is intentionally replaceable.

    Dropping and recreating the latest-run table prevents current-run QA, Section 14 validation, and
    Section 16 evidence capture from accidentally mixing the current strategy output with a prior
    latest-run strategy output.

WHY THE ARCHIVE TABLE IS NOT DROPPED HERE:
    credit_decisioning_sim.strategy_decisions_archive is the governed historical persistence layer.

    Archive behavior is controlled later in Section 12 through:
        archive_run_flag
