How many additional applicants receive an offer under the growth policy, and what do those offers do to total modeled loss? Use the two PostgreSQL programs in DBeaver and keep the applicants fixed while the lending rules change.

  1. Open a practice database. Connect DBeaver to a separate PostgreSQL database where your role can create tables and a schema. Open local copies of both SQL files. The scripts write to credit_decisioning_sim. Module 1 rebuilds its latest application table on each run. Its default SCENARIO_ONLY archive setting also replaces rows with the same scenario set, scenario name and population ID. Check the archive behavior.
  2. Build the applications once. In Module 1, find the Section 2 INSERT INTO tmp_module1_params. For this example, keep the shipped baseline values of MODULE1_V2_BASELINE_SET, BASELINE_V2, BASE_POPULATION_V1, 50,000 applications and archiving enabled. Select Sections 0–8.5 and use DBeaver’s Execute SQL Script in one session so the temporary tables stay available. Review Section 9’s product and score distributions, then confirm 50,000 archived rows in Section 10.1. Open the editable values · Module 1 parameter guide.
  3. Run the two policies. In Module 2, find the Section 2.1 INSERT INTO tmp_m2_operator_run_selector. Keep the active flag TRUE and run mode STANDARD_CAMPAIGN.
